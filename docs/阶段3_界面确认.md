## 三、抓图本身踩的坑（记下来，因为「看起来很对」的假图最危险）

本轮为了拿到一张可信截图，先后否掉了 3 种抓法：

1. **`GetWindowRect` ≠ 可见边界。** 它包含 DWM 的隐形 resize 边框。
   本机实测 `raw=(312,312,1640,1095)` 而 `DWMWA_EXTENDED_FRAME_BOUNDS` 给出
   `(319,312,1633,1088)` —— 差 7px。按 raw 截，四周会带进窗口外的内容，
   看起来「像渲染缺陷」，实际是取边界取错了。
2. **最小化窗口的 DWM 边界在 -32000 附近**（Windows 把最小化窗口放在屏幕外）。
   必须先 `SW_RESTORE`，**然后重新读一次边界**再做任何坐标校验；
   否则校验的是恢复前的坐标，结论必然错。
3. **必须做遮挡自检**：抓完要验证窗口中心点的 `WindowFromPoint` 归属进程是不是目标进程。
   本机实测多次「`GetForegroundWindow` 已是目标窗口」，但那个点仍归另一个进程 ——
   说明目标窗口虽被标为前台，却仍被置顶窗口压着。
   缺了这道校验，抓到的会是**被遮挡的别的窗口**，而图看起来完全正常。

4. **WebView2 用 `PrintWindow` 必须带 `PW_RENDERFULLCONTENT`(0x2)**，否则常得到全黑
   （WebView2 走 DirectComposition）。加了这个标志后，**不依赖窗口是否可见、是否有焦点**。

⇒ 首选方案：`PrintWindow(hwnd, hdc, 2)` + 颜色数自检（≤2 即判全黑失败）。
   本轮最终采用的就是它，因此没有被「IDE 抢前台」影响。

## 四、纠正一个此前写错的结论：多出来的 python.exe 不是「CUDA 验证子进程」

**现象**（进程树）：

```
app-ui.exe(36MB) → python.exe(4.7MB) → python.exe(664MB)
```

上一轮把第二个 python 记成了「异步 CUDA 验证子进程」。**这是错的**，本轮查清：

- 仓库内除 `locator.rs`（Rust 侧 spawn）与 `tools/rpc_smoke.py` 外，
  **没有任何地方再起 `app.rpc`**；`env_probe.verify_cuda()` 是**进程内**执行，不起子进程。
- **对照实验**：一个什么都不做的 `python -c "import time; time.sleep(12)"`，
  同样会产生一个子 python 进程。⇒ 与 Vidnote 的代码无关。
- **父子映像不同**：

  | | 映像 | 大小 | 线程 |
  |---|---|---|---|
  | 父 | `envs\default\Scripts\python.exe` | 241 KB | 4 |
  | 子 | `versions\3.13.12\python.exe` | 91 KB | 9 |

⇒ **venv 的 `Scripts\python.exe` 是一个重定向壳（redirector），会把基础解释器作为子进程重新拉起来。**
一个 worker = 两个 python 进程，是**本机解释器部署方式的正常现象**，不是泄漏。

**附带实测**：只 `kill()` 父（重定向壳）、不动子，**子也会在 3 秒内退出**，
本环境不会因此产生孤儿。（最可能的机制是管道随父关闭触发了我们已实现的 EOF 自杀，
`tools/rpc_smoke.py` 判据 19 已覆盖：实测 0.02 s。**此因果未单独验证，如实标注。**）

> 这条之所以值得单列：它同时是一次**误判**和一次**假警报**。
> 只数进程数、不看映像路径，就会把「解释器部署方式」读成「我们的子进程泄漏」。

## 六、故障态呈现（2026-10-03 补做，即 §五 里那个缺口）

### 6.1 注入方式是「真杀」，不是造一个假 state

```
taskkill /F /T /PID <venv 壳 pid>    # 壳 → 基础解释器 → conhost，三个一起走
```

宿主 `app-ui.exe` **没有被碰**。它自己在 stdout 读到 EOF 后走到 `on_worker_exit`，
写下这一行（原文，从 `tauri dev` 转发的 stderr 抓的）：

```
[worker] state → exited（worker 意外退出（code=Some(1)）。规格 §7 要求自动重启一次；当前版本先如实上报，未自动重启。）alive=false restart=0 ver=Some("0.2.0") gpu=Some(true)/Some(true)
```

`code=Some(1)` 与被 kill 的退出码一致 —— 说明这条路径读到的确实是子进程的真实退出码。

### 6.2 界面表现（截图 `docs/images/阶段3_界面-worker已退出.png`）

| 位置 | 表现 | 对应代码 |

⇒ **核心结论：崩了之后界面没有假装一切正常。** 按钮全灰、状态变红，用户不会误以为还能操作。

### 6.3 由此发现 3 个缺陷（2 个已修，1 个记录）

**缺陷 1 — 退出事件不进日志区（Rust，已修）**
`on_worker_exit` 只 `emit_state`，不发 `log` 事件。于是杀掉 worker 之后，
日志区最后一行还是崩溃前的 `环境验证：GPU 可用`，**看不出已经出事**。
⇒ `on_worker_exit` 两条分支各补一条日志；同时把 stderr 线程、心跳线程里手写的
`app.emit(EVENT_CHANNEL, json!{..})` 一并收口到新的 `Inner::emit_log()`
（避免又走成「有的路径记了、有的没记」）。

**缺陷 2 — `exited` 态看不到原因（前端，已修）**
`StatusBar.tsx` 原本只在 `state === "failed"` 时渲染 `detail`：

```tsx
{worker?.state === "failed" && (<span className="statusbar-detail" …>{worker.detail.split("\n")[0]}</span>)}
```

⇒ `exited` 时那段「意外退出（code=Some(1)）…未自动重启」**只存在于 chip 的 tooltip 里**，
界面上一个字都没有 —— 而这恰恰是用户此刻唯一想知道的事。
⇒ 条件扩为 `failed || exited`（前者失败、后者是崩溃，对用户是同一件事）。

**缺陷 3 — 没有恢复入口（产品，~~本次不改~~ → 2026-10-04 已改）**
worker 已退出时用户唯一出路是关掉应用重开。§7 的自动重启未实现。
⇒ 当时判为「属功能不属呈现，不在本次改动范围」，已记入 `PLAN §8`。
**2026-10-04 落地**，两条一起做（缺任何一条都不算修好）：

1. **自动重启（规格 §7：「自动重启一次」）** —— `worker/mod.rs::try_recover_after_crash`。
   退避 1 s 后重启，上限 1 次；用尽后停下来并**明确告诉用户还有手动那条路**。
2. **手动重启入口** —— 新增 Tauri 命令 `worker_restart` + 工具栏的「重启 worker」按钮。
   只在 `failed` / `exited` 时出现（`starting` / `restarting` 不给，避免连点把正在起来的
   进程又杀一遍）。它会清零自动重启计数与 fatal 标记 —— 那是全新的一次尝试。

配套改动见 §6.5。

### 6.5 崩溃自动重启的落地（2026-10-04）

改动落在 `app-ui/src-tauri/src/worker/mod.rs`，前端三处跟随。**判据全部在沙箱内可跑**。

| 改动 | 位置 | 为什么必须这样 |
|---|---|---|
| 决策抽成纯函数 `decide_recovery(fatal, used)` | `mod.rs` | 真正会错的就是这个判断；它住在 `try_recover_after_crash` 里（需要 `AppHandle`）就永远测不到 |
| `Inner::me: Weak<Inner>`（`Arc::new_cyclic`） | `mod.rs` | 自动重启发生在 `&self`（`on_worker_exit`）里，而 `spawn_worker` 要 `Arc<Inner>` 才能把 `Arc` 移进读线程。用 `Weak` 而非 `Arc`：强引用会成环，`Inner::drop`（负责 kill 子进程）就永不执行 |
| `Inner::heartbeat_gen` | `mod.rs` | 心跳线程改成「代号变了就退出」。**不能靠「重启时把 `stop_heartbeat` 置回 false」复用线程**——旧线程可能正睡在 5 s 里，醒来会以为自己是当前代，于是两个心跳线程同时 ping，`missed_pongs` 被数两遍、worker 提前被判死 |
| `Inner::stderr_tail`（20 行环形缓冲） | `mod.rs` | 规格 §7 要求「再失败则展示 stderr 尾部」 |
| `Inner::fatal` | `mod.rs` | 规格 §8：环境级故障不重启。⚠️ 现状 Python 侧**无人发 `fatal: true`**（`rpc.py` 刻意用 `fatal=False`），此分支按规格实现但当前不会触发 |
| `on_worker_exit` 去掉 `already_dead` 的提前 `return` | `mod.rs` | 旧逻辑下「心跳判死 → 进程随后真的退出」这条路径**永远不会重启**。两条路径描述同一次死亡，不该各有各的命运 |
| 快照新增 `pipeline_state` | `mod.rs` / `types.ts` | **三端漂移修复**：规格 §4 的 `ready` 事件本来就带 `pipeline_state`，前端 `App.tsx` 与 `types.ts` 也一直在读，只有 Rust 从未捕获 |
| 状态新增 `restarting` | 两者 | **不合并进 `starting`**：前者是「起来过又死了正在救」，后者是「从没起来过」 |
| `restart_count` 以原子量为唯一真源 | `mod.rs::emit_state` | 否则 `set_state` / 心跳线程那些「整份替换快照」的路径会把计数悄悄清零 |

**实测（沙箱内，可复跑）**：

| 判据 | 命令 | 实测 |
|---|---|---|
| 单测 13 条（新增 7 条） | `cargo test --lib` | ✅ **13 passed / 0 failed** |
| 编译（含 bin） | `cargo build` | ✅ 0 warning |

新增的 7 条单测：`first_crash_triggers_exactly_one_restart` /

### 6.6 关闭确认 / 右键菜单 / 231 提示（2026-10-04，同一轮）

**① 关闭确认 + 优雅关闭 30 s 窗口**（`PLAN §7.2` 第 3 条 / `§8` 的遗留项）

原状：点 X → 窗口关 → 应用立即退出 → `RunEvent::Exit` 里 `force_kill()` ——
而 Python 那一刻可能正在 `dispatcher.stop()` 里把任务状态写回 `state.db`。
断点续跑的正确性依赖那次写入。这就是「30 s 窗口一直拿不到」的成因。

改法：
- `CloseRequested` 里先问 `should_confirm_close()`（决策抽成纯函数
  `needs_close_confirmation`）。**要拦就 `api.prevent_close()`** —— 不拦就没有 30 s 可言。
- 拦下后发 `worker://close-requested`，前端弹模态框（继续运行 / 退出并停止任务）。
- 选「退出」→ `worker_confirm_close` → 置 `close_confirmed`（**一次性放行**，
  否则再走一遍关闭流程会无限重弹）→ 发 `shutdown` → 后台轮询 `alive`，
  **等 worker 真退出（上限 30 s，与 `rpc.py` 的 `dispatcher.stop(timeout=30.0)` 对齐）**
  才 `app.exit(0)`。等待期间界面挂「正在退出…」遮罩 —— 没有它，用户会以为卡死而强杀，
  那恰好会截断我们要保护的那次写入。

**② 行右键菜单**（`PLAN §7.2` 第 2 条）：打开输出目录 / 查看转写稿 / 重试 / 取消 / 移除。
两个实现要点：
- 菜单项与行内按钮**共用同一批回调**（`contextItems` 与 `rowActions`）——不另写一套语义。
- 关闭监听里的 `contextmenu` **必须走捕获阶段**，否则「在另一行上右键」会先开新菜单、
  再被冒泡监听关掉，现象是「右键别的行没反应」。

**③ `os error 231` 的可操作提示**：`hint_for_spawn_error` 把 231 / 5 / 2 译成提示，
**首行即动作**（状态栏只渲染首行，动作写在后面等于没给）：
> 命中 ERROR_PIPE_BUSY(231)：命名管道「读方向」被外部注入层拦截。**请改用普通终端启动本程序**
> （AI 工具沙箱内必然复现，重启系统无效）。判据：python tools\probe_spawn_env.py

**未知错误码保留系统原文**，不编一句"听起来合理"的话 —— 那会把人引到错的方向。
`locator.rs` 的「找不到 Python 解释器」同样改成首行带动作。

> **一处查过源码才敢下的决定**：「查看转写稿」**没有**用 opener 插件的 `openPath`。
> 依据（读过 `tauri-plugin-opener-2.7.0`）：`opener:default` 权限集只含
> `allow-open-url` / `allow-reveal-item-in-dir` / `allow-default-urls`，**不含 `allow-open-path`**；
> 且该命令要走 ACL 的*路径 scope* 校验，而 `work_dir` 是用户写在 `config.yaml` 里的，
> 无法静态声明。= 前端直接调必然 `ForbiddenPath`。
> 正解：crate 文档（第 8–10 行）明确写着插件的**自由函数不做 scope 校验**，故新增
> 宿主命令 `open_local_path` 代开。**既没新增 ACL 配置，也没把用户路径写死。**

**实测（沙箱内，可复跑）**：`cargo test --lib` **17/17**、`cargo build` 0 warning、
`npx tsc --noEmit` exit 0。新增 4 条单测：`close_is_confirmed_only_when_tasks_are_advancing` /
`already_confirmed_close_is_never_re_blocked` /
`pipe_busy_231_is_translated_into_an_actionable_first_line` /
`other_known_codes_get_hints_and_unknown_ones_get_none`。

> 排查编译告警时要先把它摘出去，否则会误以为改动引入了问题。

> 重启系统**没有**解决问题；真因也不是「Windows 会话的环境级异常」，
> 而是 **WorkBuddy 自己的 CLI 沙箱 `tsbx.dll` 注入了工具启动的进程，拦截了命名管道
> 客户端「读数据」方向的打开**。完整证据与更正见 **§7.7**。
> §7.1–7.4 的**实测数据仍然有效**（它们正是定位真因的台阶），但 §7.4 表格里

本节记的是一个**与 Vidnote 无关**的问题 —— 之所以写进本项目文档，
是因为它挡住了上面那些实验，而且**它的排查顺序本身就是一条教训**（§7.6）。

### 7.1 先证明「与项目代码无关」

`tauri-cli` 是 Rust 写的，它 spawn `npm run dev` 时同样中招 ⇒ 面比 Vidnote 大得多。

### 7.2 最小复现：把变量隔离到只剩一个

| **仅 stdin piped** | **FAIL 231** |
| 仅 stdout piped | OK |
| 仅 stderr piped | OK |

⇒ **与 `CREATE_NO_WINDOW` 无关、与目标程序无关，只与「stdin 管道」有关。**

### 7.3 为什么偏偏是 stdin

查 Rust 1.90 的 `library/std/src/sys/pal/windows/pipe.rs`：`anon_pipe` **不用 `CreatePipe`**，
而走 NT 原生 API（注释写明原因：`CreatePipe` 不支持 overlapped I/O）：

```rust
NtCreateNamedPipeFile(&mut ours,
    SYNCHRONIZE | if ours_readable { GENERIC_READ } else { GENERIC_WRITE },
    &object_attributes, &mut io_status,
    if ours_readable { FILE_SHARE_WRITE } else { FILE_SHARE_READ },   // ← 分岔点
    FILE_CREATE, 0, FILE_PIPE_BYTE_STREAM_TYPE, FILE_PIPE_BYTE_STREAM_MODE,
    FILE_PIPE_QUEUE_OPERATION,
    /* only allow one client pipe */ 1,
    PIPE_BUFFER_CAPACITY, PIPE_BUFFER_CAPACITY, &timeout);
```

- stdout / stderr：`ours_readable = true` → `GENERIC_READ` + `FILE_SHARE_WRITE`
- **stdin：`ours_readable = false` → `GENERIC_WRITE` + `FILE_SHARE_READ`** ← 只有它走这条

而且这条路径上 std **没有重试**：失败即 `RtlNtStatusToDosError(status)` 原样返回，
于是 `STATUS_PIPE_BUSY` 变成了 `ERROR_PIPE_BUSY (231)`。

**一个很说明问题的反证**：`cargo` 本身编译一切正常（它要 spawn `rustc`），
因为 cargo **不 pipe rustc 的 stdin**；而 `tauri-cli` pipe 了，所以它死了。

## 七之补（§7.7）、真因：`tsbx.dll` 拦截命名管道「读方向」的客户端打开

> 2026-10-04 复测（**系统已重启过**）追加。本节推翻 §7.5 的结论。

### 7.7.1 第一步：重启无效，原假设出局

重启后立刻重跑最小复现（`$TEMP\spawnprobe`，纯 std、零依赖、无 C/C++）：

```
[FAIL ] piped + CREATE_NO_WINDOW  ->  所有的管道范例都在使用中。 (os error 231)
[FAIL ] piped, 无 creation_flags  ->  所有的管道范例都在使用中。 (os error 231)
[OK  ] 不 piped, 无 flags
[FAIL ] 仅 stdin  ->  所有的管道范例都在使用中。 (os error 231)
[OK  ] 仅 stdout
[OK  ] 仅 stderr
```

⇒ **「重启系统可恢复」被实测否定**。同时用 `dangerouslyDisableSandbox: true` 跑同一探针，**仍 FAIL 231**。

### 7.7.2 第二步：把三段 NT 调用拆开，定位到**第三段**

用 Python `ctypes` 逐字复刻 `anon_pipe` 的三步（参数与 std 源码一致，含 `nMaxInstances = 1`、
空 `ObjectName`、`RootDirectory = \??\PIPE\` 句柄）：

| 步骤 | 调用 | stdin 侧（`ours_readable=false`） | stdout 侧（`ours_readable=true`） |
|---|---|---|---|
| 1 | `NtOpenFile(\??\PIPE\)` | OK | OK |
| 2 | `NtCreateNamedPipeFile` | **OK** | **OK** |
| 3 | `NtOpenFile(theirs)` | **FAIL** `0xC00000AC` = `STATUS_PIPE_BUSY` → dos **231** | OK |

⇒ 失败在 **step 3：打开管道的「客户端端」**。前两步（含被怀疑了半天的 `nMaxInstances=1`）全都正常。

**顺手排掉一个猜测**：把 `nMaxInstances` 改成 1 / 2 / 4 / 255 —— **四档全是 231**。
⇒ 与「实例被占满」无关。

### 7.7.3 第三步：换成 Win32 API，现象**一模一样**

用 `CreateNamedPipeW` + `CreateFileW`（完全不碰 Rust）复现：

| 服务端 OpenMode | 客户端 `dwDesiredAccess` | 结果 |
|---|---|---|
| `PIPE_ACCESS_OUTBOUND` | `GENERIC_READ` | **FAIL 231** |
| `PIPE_ACCESS_INBOUND` | `GENERIC_WRITE` | OK |
| `PIPE_ACCESS_DUPLEX` | `GENERIC_READ` | **FAIL 231** |
| `PIPE_ACCESS_DUPLEX` | `GENERIC_WRITE` | OK |
| `PIPE_ACCESS_DUPLEX` | `GENERIC_READ \| GENERIC_WRITE` | OK |

**连 `DUPLEX` 的客户端读都被拒** —— `DUPLEX` 按文档是允许客户端读写任意方向的，
所以这**不是 Windows 的正常行为**。

再把访问权限拆到具体权限位：

| 客户端请求的权限 | 结果 |
|---|---|
| 含 `FILE_READ_DATA` / `FILE_READ_EA` 的任意组合（含 `GENERIC_READ`、`FILE_GENERIC_READ`） | **FAIL 231** |
| `READ_CONTROL` 单独 | OK |
| `SYNCHRONIZE` 单独 | OK |
| `0`（只要元数据） | OK |

⇒ 规则精确到一句：**客户端打开命名管道，只要请求「读数据」权限就被拒，并返回伪 `STATUS_PIPE_BUSY`。**

### 7.7.4 第四步：找到拦截者 —— 注入到进程里的 `tsbx.dll`

枚举**本进程已加载的非系统模块**（这是本轮最关键的一条命令）：

```
=== 本进程（python，WorkBuddy 工具链启动）（共 65 个模块）===
  系统目录模块 51 个，非系统 14 个：
    ...\python\versions\3.13.12\python313.dll
    D:\IDE\WorkBuddy\resources\app.asar.unpacked\cli\vendor\sandbox\5.6.10\tsbx.dll   <== 可疑
```

- **子进程同样被注入**（同一个探针 spawn 的 python，模块表里也有 `tsbx.dll`）。
- **注入范围是局部的**（逐个进程查）：

| 进程 | `tsbx.dll` |
|---|---|
| `chrome.exe` / `explorer.exe` / `ZCode.exe` / **`WorkBuddy.exe`** | 无 |
| `node.exe` / `bash.exe` / `cmd.exe` / `mintty.exe` / `git-bash.exe` | 无 |
| **工具启动的 `python.exe`（及其子进程）** | **注入** |

⇒ 故障**只存在于 AI 工具的进程树内**，**不是机器级故障**。这直接解释了为什么它
「只在被工具跑的时候出现」。

- `tsbx_rules.json`（沙箱策略文件）里**只有 file / network / process 规则，没有任何管道规则**
  ⇒ 拦截是 `tsbx.dll` 的**硬编码行为**，不是可配项。语义上完全说得通：
  **禁止读别人的命名管道**是标准的沙箱逃逸防护（命名管道是经典的提权/逃逸通道）。

### 7.7.5 为什么「有的能跑有的不能」—— 全部对上了

| 现象 | 用「客户端读方向被拦」解释 |
|---|---|
| Rust `stdin(Stdio::piped())` 失败 | std 让**子进程的 stdin 走「客户端读打开」**（`anon_pipe(ours_readable=false)`）→ 正面命中 |
| Rust `stdout`/`stderr` piped 正常 | 客户端那侧是**写**方向 → 放行 |
| Python `subprocess(input=...)`（`CreatePipe`）正常 | `CreatePipe` 把**可读端做成「服务端创建」的句柄**，不走客户端读打开 |
| `cargo` 编译一切正常 | cargo **不 pipe `rustc` 的 stdin** |
| `tauri dev` 死在 spawn `npm run dev` | 它 pipe 了子进程 stdin |
| 手动 `NtCreateNamedPipeFile` 成功 | 那是**创建**，不是客户端打开 |
| 上一轮「ctypes 调 `CreateNamedPipeW` 成功」 | 同上：只测了创建，没测客户端打开 |

- **Vidnote 没有问题。** 之前所有「起不来」都发生在**工具沙箱进程树内**。

  `%TEMP%\spawnprobe\target\debug\spawnprobe.exe` —— 若全 `OK`，本条结论即闭合。

  **不是会话中途更新**。⇒ **「为什么中途变了」未查清**，不做猜测。

  （枚举非系统模块），比任何推理都快。

> —— 不要把它当成"偶发"。这一步是整条链上唯一能证伪「注入只限工具进程树」的实验。

### 7.9 打包产物的沙箱外验证（L1 / L2）

PyInstaller 产物**已在沙箱内冒烟通过**（判据与实测见 `docs/打包与分发.md`），
但那验的是「产物本身能起来、GPU 仍可用」，**验不到「Tauri 侧能不能定位到它」**。

| 级别 | 命令 | 验到哪一层 | 耗时 |
|---|---|---|---|
| **L1** | `cd app-ui` → `set VIDNOTE_BUNDLED=1` → `npm run tauri dev` | `locator.rs::locate_bundled()` 定位 + 打包产物驱动真实 GUI | 分钟级 |
| **L2** | `cd app-ui` → `npm run tauri build -- --config ../packaging/tauri.bundle.json` | **MSI** 安装包（~~NSIS~~，2026-10-05 判死）：安装目录、`worker/` 落位、快捷方式、卸载 | 十几分钟（release 编译） |

> ⚠️ **2026-10-06 应用改名 `app-ui` → `Vidnote`**：上表两行的 `cd app-ui` 是**目录名**（未改），
> 装出来的主程序名从 `app-ui.exe` 变成 **`vidnote.exe`**（安装包 / 安装目录 / 快捷方式则是
> `Vidnote`）。跑上面的验证步骤时，进程名按 `vidnote.exe` 找。

**L1 的三条判据**：

1. 状态栏 chip 出现 `worker 0.2.0` + `GPU 可用`；
2. 日志区应有 `已启动：打包产物：仓库内的 PyInstaller 产物（开发机验证 sidecar 用）`
   —— **这一行才是 L1 的核心判据**：它证明走的是 sidecar，
   而不是 `VIDNOTE_PYTHON` 指的那个 venv（两者都能让界面「看起来正常」）；
3. 任务能正常跑（可复用 §7.8 第 8–10 步，顺带把那些界面改动一起验掉）。

**若 L1 起不来**：看状态栏首行。出现
`找不到打包后的 worker：请先运行 tools/build_worker.py 生成产物`
= 三条候选都没命中；悬停状态栏 chip 看 tooltip，里面列了**每一条已尝试的路径**。

> L1 之所以成立，靠的是 `bundled_candidates()` 的第三条候选（仓库内 `build/pyinstaller/...`）。
> 它**只**服务于这个场景；普通 `tauri dev` 不会命中它 ——
> 否则就变成「改了源码却跑的是旧包」这种隐式陷阱。
>
> ⚠️ L2 需要 NSIS（Tauri 会自动下载到 `%LOCALAPPDATA%\tauri`）。
> **「无 Python 无 Rust 机器」上的运行仍未验证** —— 同机模拟不算。
