# 打包与分发

> 目标：用户机器上**既没有 Python 也没有 Rust**，装完就能用。
>
> **状态（2026-10-04）**：链路已建成，PyInstaller 产物在本机跑通并冒烟通过（§6.1）。
> **仍未验证**：NSIS 安装包本体、以及「无 Python / 无 Rust 机器」上的运行 —— 见 §6.2。

## 1. 两层结构

```
app/rpc.py ──PyInstaller(onedir)──▶ build/pyinstaller/vidnote-worker/
                                       ├── vidnote-worker.exe
                                       └── _internal/     ← 含 nvidia CUDA DLL（约 2.0 GB）
                                             │
                  packaging/tauri.bundle.json 的 bundle.resources
                                             ▼
                                 <安装目录>/worker/
                                             │
                     locator.rs::locate_bundled() 定位
                                             ▼
                                  GUI 无感启动（用户看不到 "Python"）
```

两层各管一段，少一层都不成立：

- **PyInstaller** 让用户**不需要 Python**（含 ctranslate2 的 CUDA kernels 与 cuBLAS/cuDNN DLL）；
- **Tauri bundler** 让用户**不需要 Rust**，并产出安装包、快捷方式、卸载项。

## 2. 为什么是「单目录 + resources」而不是「单文件 + externalBin」

| 方案 | 结论 |
|---|---|
| `--onefile` + `bundle.externalBin` | ❌ 单文件每次启动把约 2 GB 解压到 `%TEMP%`，冷启动几十秒；且 CUDA DLL 从临时目录加载的行为**没人验证过** |
| `--onedir` + `bundle.externalBin` | ❌ `externalBin` 只支持**单文件**；配单目录会得到一个**缺 DLL 的包** —— 而且它是「打包成功、运行才崩」 |
| `--onedir` + `bundle.resources`（目录映射到 `worker/`） | ✅ 目录结构保真 |

第三条的保真性**不是从文档得来，是读实现核过的**：
`tauri-utils-2.10.1/src/resources.rs::resource_from_path()`，map 形式 + 目录 pattern
会走 `ResourcePathsInnerIter::Walk` 分支，target = `dest.join(path.strip_prefix(pattern))`。
即 `{"../../build/pyinstaller/vidnote-worker": "worker"}` → 安装目录下
`worker/vidnote-worker.exe` + `worker/_internal/...`，**相对层级完整**。

## 3. 为什么 resources 写在独立的 overlay 配置里

`packaging/tauri.bundle.json` 只有三行，靠 `--config` 叠加：

```bash
cd app-ui
npm run tauri build -- --config ../packaging/tauri.bundle.json
```

**不写进 `tauri.conf.json` 的原因**（这一条踩过就知道有多贵）：
`tauri-build` 的 `copy_resources()` 在 `build()` 里**无条件执行** ——
`cargo build` 每编译一次就复制一遍 resources。后果有两个：

1. 每次编译多复制约 2.1 GB；
2. **PyInstaller 产物还没生成时，`cargo build` 直接失败**（`Error::ResourcePathNotFound`）
   —— 即「不打包 Python 就没法编译 Rust」，把两件本该独立的事绑死了。

⚠️ 所以**你不会**在 `tauri.conf.json` 里找到 `resources`。那不是漏了。

## 4. 构建

```bash
# 1) Python 侧 —— 必须用装齐依赖的那个解释器（仓库里没有 .venv）
C:/Users/Ben/.workbuddy/binaries/python/envs/default/Scripts/python.exe tools/build_worker.py

# 2) Tauri 侧 —— 叠加打包配置
cd app-ui
npm run tauri build -- --config ../packaging/tauri.bundle.json
```

`tools/build_worker.py` 不只是包一层 PyInstaller，它做四件事，**每件都自己报告判据**：

| 阶段 | 判据 |
|---|---|
| 前置校验 | 解释器 / Python 版本 / 9 个依赖的版本与**实际路径** / CUDA DLL 三类各有几个、共多少 MiB |
| 打包 | PyInstaller 退出码 + 耗时 |
| 产物校验 | `vidnote-worker.exe`、`_internal/`、`cublas64_12.dll`、`cudnn64_9.dll`、`ctranslate2.dll` 逐个存在性 + 总体积下限 |
| **冒烟** | 真起一次：`hello → ready`（含 `config_is_default` 必须为 false）、`ping → pong`、**等 `env_verified`**（真实推理验证 GPU）、`shutdown → bye` |

`--check-only` 只跑第一段（秒级，不写盘）；`--smoke-only` 只跑最后一段。

### 冒烟为什么要用匿名管道

本工具的沙箱拦截**命名管道客户端读方向**的打开（`os error 231`），
而 Rust 的 `Stdio::piped()` 正好走那条路 —— 这就是 `app-ui` 在沙箱内起不来的原因。
Python 的 `subprocess.PIPE` 走 `CreatePipe`（**匿名**管道），
2026-10-04 实测**不受影响**（`Popen(stdin=PIPE, stdout=PIPE)` 往返成功）。
所以这个脚本在沙箱内外都能跑出可信结论。

## 5. 打包模式下的路径重定向

**这是打包后第一个必然踩的坑**，也是「装上能启动、一跑就崩」的典型成因。

`Path.cwd()` 在安装后是 `C:\Program Files\...`（**不可写**），
而 `config.yaml` / `work_dir` / `model_dir` 原先一律锚定「项目根 = cwd」。
于是打包后第一次落盘就失败，报错还是「建不出 `work/<dir>`」这种绕远的样子。

解法收敛在**一个模块** `app/core/paths.py`（frozen 感知）：

| 函数 | 源码运行 | 打包运行 |
|---|---|---|
| `app_root()` | `Path.cwd()`（= 仓库根） | `%LOCALAPPDATA%\Vidnote` |
| `program_dir()` | `Path.cwd()` | exe 所在目录（**只读**） |
| `app_data_dir()` | `Path.cwd()` | `%LOCALAPPDATA%\Vidnote` |

配套改动只有三处，且**非 frozen 时行为逐字不变**（阶段 1/2 的判据不受影响）：

1. `models/config.py::load_or_default(path, root=None)` 新增 `root`，**只在回退分支生效**
   （文件存在时锚点是配置文件自己的目录，不能被调用方覆盖）；
2. `rpc.py` / `cli.py` 的入口改用 `paths.resolve_config_path()` ——
   优先级 `--config` / `VIDNOTE_CONFIG` > 打包时的数据目录 > 原逻辑（返回 `None`）；
3. `core/cuda_dll.py` 增加打包下的查找兜底：`sys._MEIPASS/nvidia/<pkg>/bin`。
   **不能只靠 `import nvidia`**：命名空间包在 frozen 下的 `__path__` 由
   PyInstaller 的 FrozenImporter 决定，不如显式路径可靠。

首次打包运行会自动在 `%LOCALAPPDATA%\Vidnote\config.yaml` 生成一份可编辑的默认配置，
`work_dir` / `model_dir` 落在同一目录下。

⚠️ **模型不进包**（`large-v3` 是 3 GB）。所以打包后的 `model_dir` 默认指向数据目录，
用户需自行把模型放进去或改 `config.yaml` 指到已有模型 —— 缺失时 `pipeline` 会给出下载指引。

### 5.1 打包模式下必须做的第二件事：主线程预热原生依赖

`rpc.py::serve()` 在**主线程**调 `env_probe.warmup_native_deps()`，
把 `cuda_dll / numpy / ctranslate2 / onnxruntime / av / faster_whisper` 全部 import 掉。

不做的话：打包产物里**非主线程**的首次原生 import 会**静默卡死 2 分钟以上**，
而主线程里只要 2.03 s —— 现象、定位流程与对照数据见 **§7.3**。
代价是 `ready` 晚约 2 s。

## 7. 实测记录

### 7.1 构建与冒烟（2026-10-04）

```
前置校验：解释器 / 9 个依赖 / CUDA DLL 2009 MiB            全 ok
打包    ：PyInstaller 退出码 0，耗时 59 s
产物    ：2475 MiB（exe 15.8 MiB + _internal/）
冒烟    ：28/28 判据通过
  [ok] hello → ready：server_version=0.2.0 gpu_usable=True config_is_default=False
  [ok] 配置来源：读到了指定 config（没有回落到默认值）
  [ok] ping → pong（协议往返）
  [ok] env_verified：gpu_usable=True —— 真实推理通过（输入 1.0s，device=cuda）
  [ok] shutdown → bye（优雅退出）
```

**最高风险项至此闭环**：CUDA DLL 随 PyInstaller 分发后，**真实推理仍然跑通** ——
不是 `device_count` 那种只看硬件的快判，是真的把 large-v3 加载起来跑了一次。

回归：`tools/rpc_smoke.py` **19/19**、`tools/dispatcher_selftest.py` **53/53**、
`cargo test --lib` **20/20**。

### 7.2 踩到并修掉的四个坑

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 沙箱内打包**退出码 1**，终端只留一句「PyInstaller 失败」 | PyInstaller 覆盖旧产物时 `rmtree` 2083 个文件，命中受管环境的**批量删除保护**（阈值 50） | 构建前**改名旁置**旧产物（一次系统调用，不计数）。见 `stash_previous()` |
| 2 | 同上，**查不到原因** | `--log-level WARN` 吞掉了「哪个 hook 没找到」；`2>&1 \| tail -20` 又把中段截掉 | PyInstaller 输出**落盘**到 `build/pyinstaller.log`，失败时打印尾部 40 行 |
| 3 | 打包产物里 `env_verified` **永不推送**，界面永远停在「验证中」 | `verify_cuda` 静默卡死，daemon 线程无异常无 traceback，**零可观测性** | ① `verify_cuda` 加分步 `_tick` 打点；② `VIDNOTE_FAULTHANDLER=<秒>` 开关；③ `_verify_env` 加 **120 s 看门狗**，超时如实上报「未知」（不是「不可用」） |
| 4 | 卡死本身 | **见 §7.3** | 主线程预热原生依赖 |

### 7.3 根因：打包产物里「非主线程的首次原生 import」会静默卡死

这是本次最有价值的发现，**跨阶段有效**（阶段 4 / 5 同样会踩）。

**现象**：打包产物启动后，`_verify_env` 的 daemon 线程里 `import numpy` 卡死 > 2 分钟；
同一份 `_internal` 在 venv 下只要 **0.3 s**。

**定位手段**（顺序很重要，前一步做不到就上后一步）：

1. **打点**：只能知道「卡在 import 区间」，不够 → 上 faulthandler
2. **`faulthandler`**：`VIDNOTE_FAULTHANDLER=20` → 拿到真实栈，
   停在 `numpy/__config__.py:4` → `numpy/_core/_multiarray_umath.pyd` 的**原生加载**
3. **对照实验**：`VIDNOTE_IMPORT_PROBE=1` 在主线程逐个 import，每步立即上报

**对照结果**（同一份产物、同一次启动）：

| 位置 | 结果 |
|---|---|
| daemon 线程 `import numpy` | **卡死 > 120 s** |
| 主线程逐个 import（6 个依赖） | **2.03 s**（numpy 0.30 / onnxruntime 0.21 / av 1.46 / 其余 ≈0） |

**处置**：`env_probe.warmup_native_deps()` 在 **`serve()` 的主线程**里把
`cuda_dll / numpy / ctranslate2 / onnxruntime / av / faster_whisper` 全部 import 掉。

**为什么是无条件的，而不是「只在 CUDA 验证前」**：
`dispatcher` 的阶段函数（下载 / 转写 / 抽帧）跑在**工作线程**里，
首次 `import faster_whisper` 会踩同一个坑 —— 表现是「点了开始，任务永远停在 0%」。
所以预热与 `runtime.device` 配置无关。

**代价**：`ready` 晚约 2 s（打包产物）/ 约 0.36 s（源码运行，实测）。

> ⚠️ 这条的**机制尚未查明**（PyInstaller 的 frozen importer 在非主线程下的行为？
> 还是 OpenBLAS 线程池在非主线程初始化？）——目前只有**现象与对照数据**，
> 没有根因级解释。所以 §7.4 的开关要一直留着：换 PyInstaller 版本时必须重跑一次 probe。

### 7.4 留下的诊断开关（都默认关闭，零运行时开销）

| 环境变量 | 作用 | 为什么留着 |
|---|---|---|
| `VIDNOTE_FAULTHANDLER=<秒>` | 定期把全部线程栈 dump 到 stderr | 原生卡死时唯一能看到「卡在哪一行」的手段 |
| `VIDNOTE_IMPORT_PROBE=1` | 主线程逐个 import 关键依赖并报耗时 | 一次区分「非主线程问题」与「打包本身问题」 |
| `VIDNOTE_LOG_STDERR=1` | 日志同时镜像到 stderr（带时间戳） | 不开 UI 时直接看 worker 输出；看出「卡在哪一条之后」 |

它们不是调试残留：`tools/build_worker.py --stderr-log` 与本文档的排查流程都依赖它们，
而 §7.3 的机制还没查清。

### 7.5 旁置产物需要人工清理

`stash_previous()` 只改名、不删除（删除会撞批量删除保护），所以每构建一次
`build/` 下会多一份约 2.5 GiB 的 `*.old-<时间戳>`。**脚本不代删**，
末尾会打印路径与清理命令。实测 4 次构建后 `build/` 已达 13 GiB。

```bash
# 在沙箱外的普通终端执行
cmd /c rmdir /s /q "D:\Code\SideProject\Vidnote\build\pyinstaller\vidnote-worker.old-20261004-025412"
```

## 8. 体积

| 组成 | 实测 |
|---|---|
| `nvidia/cublas/bin` | 736 MiB |
| `nvidia/cudnn/bin` | 1095 MiB（其中 `cudnn_engines_precompiled64_9.dll` 单个 504 MiB） |
| `nvidia/cuda_nvrtc/bin` | 178 MiB |
| **CUDA DLL 合计** | **2009 MiB** |
| 其余（ctranslate2 / av / onnxruntime / numpy / tokenizers / Python 运行时） | 见 §7 实测记录 |
| `models/large-v3`（**不进包**，运行时下载） | 2.9 GiB |

**刻意没做的瘦身**：cudnn 那 10 个 DLL 里哪些是 ctranslate2 真正必需的，
**没有实测依据**。按名字猜（「`cudnn_adv` 是 RNN 用的，transformer 用不到」）能减掉 270 MiB，
但猜错的后果是「能打包、一跑就崩」，而这恰好是本次要验证的那个风险。
瘦身的门槛是**删了以后真实转写仍然 GPU 可用**，不是「体积变小了」。
