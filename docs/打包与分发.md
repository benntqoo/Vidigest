## 1. 两层结构

```
app/rpc.py ──PyInstaller(onedir)──▶ build/pyinstaller/vidigest-worker/
                                       ├── vidigest-worker.exe
                                       └── _internal/     ← 含 nvidia CUDA DLL（约 2.0 GB）
                                             │
                  packaging/tauri.bundle.json 的 bundle.resources
                                             ▼
                                 <安装目录>/worker/
                                             │
                     locator.rs::locate_bundled() 定位
                                             ▼
                                  GUI 无感启动（用户看不到 "Python"）
```

两层各管一段，少一层都不成立：

- **PyInstaller** 让用户**不需要 Python**（含 ctranslate2 的 CUDA kernels 与 cuBLAS/cuDNN DLL）；
- **Tauri bundler** 让用户**不需要 Rust**，并产出安装包、快捷方式、卸载项。

### 1.1 安装后的 `worker/` 是什么（2026-10-26 补）

装完在 `<安装目录>\\` 下会看到两样东西：

```
vidigest.exe          ← Tauri 主程序（UI + 监督器），约 4.7 MB
worker\\               ← Python 功能层，约 2.4 GB / 2000+ 文件
  vidigest-worker.exe   PyInstaller onedir 的入口（约 14 MB）
  _internal\\           Python 解释器 + 全部第三方依赖 + CUDA/cuDNN DLL
```

**为什么必须有它**：架构是「Rust 做 UI、Python 干重活」。转写/下载/抽帧/汇总全在 Python
（faster-whisper + CTranslate2 + yt-dlp），Tauri 的 `bundle.resources` 就是把整个
`build/pyinstaller/vidigest-worker/` 目录映射到安装目录的 `worker/`。

**它不是可选组件**：主程序启动就 spawn `worker\\vidigest-worker.exe`，用 stdin/stdout 的
JSON Lines 通信（零端口）。删掉 / 改名 / 只留 exe 不带 `_internal/`，应用都起不来，
状态栏显示「worker 启动失败」。

**为什么不合成一个文件**：onefile 每次启动都解压到临时目录，冷启动多 5–15 s，且对杀软敏感；
onedir 解压一次、启动直接跑。

## 2. 为什么是「单目录 + resources」而不是「单文件 + externalBin」

| 方案 | 结论 |
|---|---|
| `--onefile` + `bundle.externalBin` | ❌ 单文件每次启动把约 2 GB 解压到 `%TEMP%`，冷启动几十秒；且 CUDA DLL 从临时目录加载的行为**没人验证过** |
| `--onedir` + `bundle.externalBin` | ❌ `externalBin` 只支持**单文件**；配单目录会得到一个**缺 DLL 的包** —— 而且它是「打包成功、运行才崩」 |
| `--onedir` + `bundle.resources`（目录映射到 `worker/`） | ✅ 目录结构保真 |

第三条的保真性**不是从文档得来，是读实现核过的**：
`tauri-utils-2.10.1/src/resources.rs::resource_from_path()`，map 形式 + 目录 pattern
会走 `ResourcePathsInnerIter::Walk` 分支，target = `dest.join(path.strip_prefix(pattern))`。
即 `{"../../build/pyinstaller/vidigest-worker": "worker"}` → 安装目录下
`worker/vidigest-worker.exe` + `worker/_internal/...`，**相对层级完整**。

## 3. 为什么 resources 写在独立的 overlay 配置里

`packaging/tauri.bundle.json` 只有 `resources` 和 `targets` 两项，靠 `--config` 叠加：

```bash
cd app-ui
npm run tauri build -- --config ../packaging/tauri.bundle.json
```

**不写进 `tauri.conf.json` 的原因**（这一条踩过就知道有多贵）：
`tauri-build` 的 `copy_resources()` 在 `build()` 里**无条件执行** ——
`cargo build` 每编译一次就复制一遍 resources。后果有两个：

1. 每次编译多复制约 2.1 GB；
2. **PyInstaller 产物还没生成时，`cargo build` 直接失败**（`Error::ResourcePathNotFound`）
   —— 即「不打包 Python 就没法编译 Rust」，把两件本该独立的事绑死了。

⚠️ 所以**你不会**在 `tauri.conf.json` 里找到 `resources`。那不是漏了。

## 3.1 为什么 `targets` 只有 MSI，没有 NSIS

**结论：2.5 GiB 的载荷装不进 NSIS，这是 NSIS 的硬限制，不是配置问题。**

2026-10-05 实测（两次，只差压缩算法）：

```
Running makensis to produce ...\bundle\nsis\app-ui_0.1.0_x64-setup.exe
Internal compiler error #12345: error mmapping datablock to 33618567.
failed to bundle project: `Failed to bundle app with makensis`
```

| 尝试 | `windows.nsis.compression` | 结果 |
|---|---|---|
| 1（Tauri 默认） | `lzma` | 报错 `error mmapping datablock to 33618567` |
| 2 | `zlib` | **报错一字不差**，连数字 `33618567` 都一样 |

换算法无效的机制（看过生成脚本，不是猜的）：
`target/release/nsis/x64/installer.nsi` 第 13 行是

```nsis
SetCompressor /SOLID "zlib"
```

—— **`/SOLID` 是 Tauri 模板写死的**，与选哪个算法无关。solid 模式要求把全部待装文件的
**未压缩**流一次性 mmap；32 位 makensis 给不出这个地址空间。

上游依据：NSIS 官方 bug [#1284](https://sourceforge.net/p/nsis/bugs/1284/)，
作者 Anders 的原话是 *"We are limited to 2gb of compressed data because we use the top bit"*，
并明确 *"It does not check the size of the uncompressed files, it hopes they compress enough to fit in 2gb"*。
我们的载荷是 **2475 MiB 未压缩**，早已超线。

**MSI 没有这个问题**：WiX 的 cab 分块压缩，实测（2026-10-05）产出
~~`app-ui_0.1.0_x64_en-US.msi`~~ → 改名后为 `Vidnote_0.1.0_x64_en-US.msi` =
**1.45 GiB**（2.5 GiB 压到 58%），退出码 0。

### 如果将来一定要 `-setup.exe`

需要先把**未压缩**载荷降到 2 GiB 以下，也就是砍掉 430 MiB+。可选方向：

| 方向 | 代价 |
|---|---|
| 裁剪 `cudnn/bin` 那 10 个 DLL | 按名字猜能减约 270 MiB，**不够**；且猜错的后果是「能装、一跑就崩」 |
| 改用系统已有的 CUDA 运行时 | 需要用户自装 CUDA，违背「装上就能用」 |
| 发 CPU 版 | 载荷骤降，但失去 8.7× 加速 —— 那是这个项目的核心价值 |
| 自维护 NSIS 模板（去掉 `/SOLID`） | Tauri 不支持覆盖内置模板，得 fork `tauri-cli` |

在这些之前，**不要**回头改 `compression` —— 已验证无效，只会白花 5 分钟。

## 3.2 版本号（2026-10-26）

产物的文件名带版本号（`Vidigest_0.2.0_x64_en-US.msi`），版本来源只有一处：仓库根的
`VERSION`。改版本：

它会同时改 `VERSION`、`tauri.conf.json`（MSI 的产品版本，控制面板显示的就是它）、

## 4. 构建

### 4.1 一键：`dev.sh`

```bash
./dev.sh release      # 完整分发形态：worker + Tauri 安装包
./dev.sh bundle-dev   # 不重新打包，用已有 worker 产物驱动 GUI（L1 验证）
./dev.sh dev          # 日常开发（venv 驱动）
./dev.sh worker       # 只打包 Python worker（含 28 项冒烟）
./dev.sh check        # 跑全部判据，不写产物
./dev.sh clean        # 列出可清理的旁置产物（--yes 才真删）
```

通用开关：`--dry-run`（只打印将执行的命令）、`--skip-worker`（release 复用已有产物）、`-y`。

Windows 上从 cmd / PowerShell 调：

```
bash dev.sh release
```

脚本解决的是**三个环节之间的隐式耦合**，不是省几次敲键盘：

| 环节 | 独立判据 | 耦合点 |
|---|---|---|
| PyInstaller | `build_worker.py` 自报 28 项 | 产物不存在 → 下一步 `cargo build` 直接失败 |
| cargo compile | `cargo build` 退出码 | `copy_resources()` **每次编译都执行** |
| Tauri bundle | 安装包本体 | cwd 必须是 `app-ui`，`--config` 相对 cwd 解析 |

另外两件它替人做的判断：

- **选解释器用「能不能 `import faster_whisper`」做判据**，不是「文件在不在」。
  本机的托管 3.13.12 与系统 3.13 都没装依赖，只判存在性会选中它们，
  然后在 PyInstaller 中途才失败，报错样子离真因很远（2026-10-03 踩过）。
  可用 `VIDIGEST_PYTHON=<路径>` 覆盖。
- **失败时打印「失败于：<步骤名>（退出码 N）」**。否则 `set -e` 静默退出，
  分不清是 npm、cargo 还是 PyInstaller 挂了。

### 4.2 等价的手工命令

```bash
# 1) Python 侧 —— 必须用装齐依赖的那个解释器（仓库里没有 .venv）
C:/Users/Ben/.workbuddy/binaries/python/envs/default/Scripts/python.exe tools/build_worker.py

# 2) Tauri 侧 —— 叠加打包配置
cd app-ui
npm run tauri build -- --config ../packaging/tauri.bundle.json
```

`tools/build_worker.py` 不只是包一层 PyInstaller，它做四件事，**每件都自己报告判据**：

| 阶段 | 判据 |
|---|---|
| 前置校验 | 解释器 / Python 版本 / 9 个依赖的版本与**实际路径** / CUDA DLL 三类各有几个、共多少 MiB |
| 打包 | PyInstaller 退出码 + 耗时 |
| 产物校验 | `vidigest-worker.exe`、`_internal/`、`cublas64_12.dll`、`cudnn64_9.dll`、`ctranslate2.dll` 逐个存在性 + 总体积下限 |
| **冒烟** | 真起一次：`hello → ready`（含 `config_is_default` 必须为 false）、`ping → pong`、**等 `env_verified`**（真实推理验证 GPU）、`shutdown → bye` |

`--check-only` 只跑第一段（秒级，不写盘）；`--smoke-only` 只跑最后一段。

### 冒烟为什么要用匿名管道

本工具的沙箱拦截**命名管道客户端读方向**的打开（`os error 231`），
而 Rust 的 `Stdio::piped()` 正好走那条路 —— 这就是 `app-ui` 在沙箱内起不来的原因。
Python 的 `subprocess.PIPE` 走 `CreatePipe`（**匿名**管道），
2026-10-04 实测**不受影响**（`Popen(stdin=PIPE, stdout=PIPE)` 往返成功）。
所以这个脚本在沙箱内外都能跑出可信结论。

## 5. 打包模式下的路径重定向

**这是打包后第一个必然踩的坑**，也是「装上能启动、一跑就崩」的典型成因。

`Path.cwd()` 在安装后是 `C:\Program Files\...`（**不可写**），
而 `config.yaml` / `work_dir` / `model_dir` 原先一律锚定「项目根 = cwd」。
于是打包后第一次落盘就失败，报错还是「建不出 `work/<dir>`」这种绕远的样子。

解法收敛在**一个模块** `app/core/paths.py`（frozen 感知）：

| 函数 | 源码运行 | 打包运行 |
|---|---|---|
| `app_root()` | `Path.cwd()`（= 仓库根） | `%LOCALAPPDATA%\Vidigest` |
| `program_dir()` | `Path.cwd()` | exe 所在目录（**只读**） |
| `app_data_dir()` | `Path.cwd()` | `%LOCALAPPDATA%\Vidigest` |

配套改动只有三处，且**非 frozen 时行为逐字不变**（阶段 1/2 的判据不受影响）：

1. `models/config.py::load_or_default(path, root=None)` 新增 `root`，**只在回退分支生效**
   （文件存在时锚点是配置文件自己的目录，不能被调用方覆盖）；
2. `rpc.py` / `cli.py` 的入口改用 `paths.resolve_config_path()` ——
   优先级 `--config` / `VIDIGEST_CONFIG` > 打包时的数据目录 > 原逻辑（返回 `None`）；
3. `core/cuda_dll.py` 增加打包下的查找兜底：`sys._MEIPASS/nvidia/<pkg>/bin`。
   **不能只靠 `import nvidia`**：命名空间包在 frozen 下的 `__path__` 由
   PyInstaller 的 FrozenImporter 决定，不如显式路径可靠。

首次打包运行会自动在 `%LOCALAPPDATA%\Vidigest\config.yaml` 生成一份可编辑的默认配置，
`work_dir` / `model_dir` 落在同一目录下。

⚠️ **模型不进包**（`large-v3` 是 3 GB）。所以打包后的 `model_dir` 默认指向数据目录，
用户需自行把模型放进去或改 `config.yaml` 指到已有模型 —— 缺失时 `pipeline` 会给出下载指引。

### 5.1 打包模式下必须做的第二件事：主线程预热原生依赖

`rpc.py::serve()` 在**主线程**调 `env_probe.warmup_native_deps()`，
把 `cuda_dll / numpy / ctranslate2 / onnxruntime / av / faster_whisper` 全部 import 掉。

不做的话：打包产物里**非主线程**的首次原生 import 会**静默卡死 2 分钟以上**，
而主线程里只要 2.03 s —— 现象、定位流程与对照数据见 **§7.3**。
代价是 `ready` 晚约 2 s。

### 6.3 卸载清理用户数据（2026-10-26 重写：旧方案实测失败）

**行为**：真卸载时删除 `<LocalAppData>\Vidigest`（`state.db` / `config.yaml` / 数据目录内的
`work/` 与 `models/`）**和** `<LocalAppData>\com.benntqoo.vidigest`（WebView2 的 user data，
实测 70 MB）；**升级安装不删**。

#### 旧方案（WiX `util:RemoveFolderEx`）为什么失败 —— 实测证据

2026-10-26 卸载后检查：`%LOCALAPPDATA%\Vidigest` **原封不动**
（`config.yaml` mtime 仍是 2026-10-24 03:20，`state.db` 仍是 10-10），
但程序目录、ARP 注册项、快捷方式、`HKCU\Software\benntqoo` 全干净 ——
说明组件装进去了、也被移除了，只有「删目录」那一步没生效。

用 `dark.exe` 反编译 MSI 拿到真因：

```xml
<Custom Action="SetVIDIGEST_APPDATA_DIR" Before="CostFinalize">NOT UPGRADINGPRODUCTCODE</Custom>
```

`[LocalAppDataFolder]` 是**目录属性，由 `CostFinalize` 这个动作才填出来**。SetProperty 排在它
**之前**，格式化拿到的是空串 ⇒ `RemoveFolderEx` 去删一个不存在的路径 ⇒ **静默成功、什么都没删**，
日志里也没有任何错误。

> 教训：MSI 侧的失败几乎都是**静默**的。凡是靠属性格式化拼路径的动作，都要问一句
> 「这个属性在我执行的那一刻被填出来了吗」。

#### 新方案：交给应用自己删

`vidigest.exe --cleanup-appdata`（`app-ui/src-tauri/src/cleanup.rs`）：

- 路径自己算，**没有属性格式化的时序问题**；
- 本地可实测（下节有命令），不必等装/卸一轮；
- MSI 侧只剩一行自定义动作：

```xml
<CustomAction Id="CleanupAppData" FileKey="Path" ExeCommand="--cleanup-appdata"
              Execute="deferred" Impersonate="yes" Return="ignore" />
<Custom Action="CleanupAppData" Before="RemoveFiles">REMOVE="ALL" AND NOT UPGRADINGPRODUCTCODE</Custom>
```

- `Before="RemoveFiles"`：那时 `vidigest.exe` 还在，调得动；
- `Return="ignore"`：清理失败不该让卸载中断（程序文件已经删了，再弹「卸载失败」只会误导）；
- `Impersonate="yes"`：以**发起卸载的用户**身份跑，否则 `%LOCALAPPDATA%` 指向 SYSTEM；
- 守卫 `NOT UPGRADINGPRODUCTCODE` 与模板自带的 `RemoveShortcuts` 同一个 ——
  MSI 的 major upgrade 是「先卸旧再装新」，不加守卫**每次升级都会清掉配置与任务历史**。

模板 `app-ui/src-tauri/wix/main.wxs` 仍是 `tauri-bundler 2.10.1` 的副本，但**已不需要
`xmlns:util`**；配在 `packaging/tauri.bundle.json` 的 `windows.wix.template`（cwd 相对，
打包时 cwd = `app-ui/src-tauri`）。

#### 已验证 / 未验证（分开写清）

| 项 | 状态 | 怎么验的 |
|---|---|---|
| 清理逻辑本身 | ✅ 已实测 | 造一份假数据目录，`VIDIGEST_CLEANUP_ROOT=<tmp> vidigest.exe --cleanup-appdata` → 两个目录消失、退出码 0、其余文件不动 |
| 开关识别 | ✅ 单测 | `cargo test --lib` 的 `flag_is_recognized_anywhere_in_argv` / `ordinary_launch_is_not_cleanup`（漏判 = 正常启动就删数据） |
| MSI 能被编译 | ✅ | `candle` / `light` 通过 |
| **MSI 会在卸载时真的调用它** | ❌ 未验证 | 装/卸要提权 + GUI。判据：装 → 卸载 → `%LOCALAPPDATA%\Vidigest` 消失 |
| **升级不删** | ❌ 未验证 | 装 vA → 双击 vB → `config.yaml` / `state.db` 还在 |

**已知残留风险**：`Impersonate="yes"` 下 `%LOCALAPPDATA%` 是**发起卸载那个用户**的。
越肩提权（标准用户 + 管理员凭据）时删的是管理员账号的数据目录。

**卸载删什么、留什么（2026-10-26 定稿）**：

| 目标 | 处置 | 理由 |
|---|---|---|
| `<LocalAppData>\Vidigest`（config.yaml / state.db） | **删** | 状态；重装要干净配置 + 空任务库 |
| `<LocalAppData>\com.benntqoo.vidigest`（WebView2） | **删** | 缓存，实测留 ~70 MB |

对话框（自定义 WiX `Dialog` + `Publish` + UI 扩展），而装/卸**本机验不了**（提权 + GUI）。
写错的后果是数据被**静默删掉** —— 上一版 `RemoveFolderEx` 就是这么栽的。
「默认保留」省掉一次点击，且能用 `VIDIGEST_CLEANUP_EXE_DIR` 在本机实测。

（都不碰模型），那里可见、可确认、可测。

### 7.2 踩到并修掉的四个坑

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 沙箱内打包**退出码 1**，终端只留一句「PyInstaller 失败」 | PyInstaller 覆盖旧产物时 `rmtree` 2083 个文件，命中受管环境的**批量删除保护**（阈值 50） | 构建前**改名旁置**旧产物（一次系统调用，不计数）。见 `stash_previous()` |
| 2 | 同上，**查不到原因** | `--log-level WARN` 吞掉了「哪个 hook 没找到」；`2>&1 \| tail -20` 又把中段截掉 | PyInstaller 输出**落盘**到 `build/pyinstaller.log`，失败时打印尾部 40 行 |
| 3 | 打包产物里 `env_verified` **永不推送**，界面永远停在「验证中」 | `verify_cuda` 静默卡死，daemon 线程无异常无 traceback，**零可观测性** | ① `verify_cuda` 加分步 `_tick` 打点；② `VIDIGEST_FAULTHANDLER=<秒>` 开关；③ `_verify_env` 加 **120 s 看门狗**，超时如实上报「未知」（不是「不可用」） |
| 4 | 卡死本身 | **见 §7.3** | 主线程预热原生依赖 |

### 7.3 根因：打包产物里「非主线程的首次原生 import」会静默卡死

这是本次最有价值的发现，**跨阶段有效**（阶段 4 / 5 同样会踩）。

**现象**：打包产物启动后，`_verify_env` 的 daemon 线程里 `import numpy` 卡死 > 2 分钟；
同一份 `_internal` 在 venv 下只要 **0.3 s**。

**定位手段**（顺序很重要，前一步做不到就上后一步）：

1. **打点**：只能知道「卡在 import 区间」，不够 → 上 faulthandler
2. **`faulthandler`**：`VIDIGEST_FAULTHANDLER=20` → 拿到真实栈，
   停在 `numpy/__config__.py:4` → `numpy/_core/_multiarray_umath.pyd` 的**原生加载**
3. **对照实验**：`VIDIGEST_IMPORT_PROBE=1` 在主线程逐个 import，每步立即上报

**对照结果**（同一份产物、同一次启动）：

| 位置 | 结果 |
|---|---|
| daemon 线程 `import numpy` | **卡死 > 120 s** |
| 主线程逐个 import（6 个依赖） | **2.03 s**（numpy 0.30 / onnxruntime 0.21 / av 1.46 / 其余 ≈0） |

**处置**：`env_probe.warmup_native_deps()` 在 **`serve()` 的主线程**里把
`cuda_dll / numpy / ctranslate2 / onnxruntime / av / faster_whisper` 全部 import 掉。

**为什么是无条件的，而不是「只在 CUDA 验证前」**：
`dispatcher` 的阶段函数（下载 / 转写 / 抽帧）跑在**工作线程**里，
首次 `import faster_whisper` 会踩同一个坑 —— 表现是「点了开始，任务永远停在 0%」。
所以预热与 `runtime.device` 配置无关。

**代价**：`ready` 晚约 2 s（打包产物）/ 约 0.36 s（源码运行，实测）。

> ⚠️ 这条的**机制尚未查明**（PyInstaller 的 frozen importer 在非主线程下的行为？
> 还是 OpenBLAS 线程池在非主线程初始化？）——目前只有**现象与对照数据**，
> 没有根因级解释。所以 §7.4 的开关要一直留着：换 PyInstaller 版本时必须重跑一次 probe。

### 7.4 留下的诊断开关（都默认关闭，零运行时开销）

| 环境变量 | 作用 | 为什么留着 |
|---|---|---|
| `VIDIGEST_FAULTHANDLER=<秒>` | 定期把全部线程栈 dump 到 stderr | 原生卡死时唯一能看到「卡在哪一行」的手段 |
