# 架构决策记录（ADR）

本目录存放**不可从代码看出的决策**：改产品形态、改架构前提、改已定稿的边界。
能被代码或测试说明的事，不写 ADR。

## 什么时候必须写 ADR

- 变更**架构前提**（例如：引入端口 / 引入本地 HTTP 服务 / 把常驻 worker 的生命周期交给别的进程）。
- 变更**产品形态或边界**（例如：把某个「不做」改成「暂不做」、引入账号/云端/多租户）。
- 推翻或修订 `docs/工程约定.md` 里标注「已定稿，不再讨论」的条目。

## 命名与编号

- 文件名：`NNNN-短标题.md`（4 位递增编号，中文短标题，用连字符分隔）。
- 编号**永不复用**；被推翻的 ADR **不删除**，改为把状态标记为「已被 ADR-XXXX 取代」。
- 状态取值：`提议中` / `已接受` / `已接受（部分暂缓）` / `已被 ADR-XXXX 取代` / `已废弃`。

## 模板（最小可用的九节）

| # | 节 | 要写什么 |
|---|---|---|
| 1 | 元信息 | 编号 / 日期 / 状态 / 决策者 / 触发 / 相关文档 / 影响范围（**是否改动代码**） |
| 2 | 背景与问题 | 现有前提是什么、新需求要求什么、**冲突点具体在哪一行** |
| 3 | 决策驱动因素 | 按优先级列出；必须含「不能破坏什么」 |
| 4 | 考虑的选项 | 每项写清**成本 / 是否破坏前提 / 生命周期归谁**；不确定的标「未实测」 |
| 5 | 决策 | 用 `D-1 / D-2 / …` 编号，每条一句话可说清 |
| 6 | 后果 | 分「正面 / 负面 / 中性」；**负面必须写**，否则这份 ADR 没意义 |
| 7 | 重开条件 | **必须是可观测事件**（某个里程碑达成、某项实测结果），不能写「等有空」 |
| 8 | 未决问题 | 明确列出推给别的 ADR 的问题，并给出归属编号 |
| 9 | 未验证 / 诚实边界 | 哪些是推断、哪些实测过。**推断不得写成已验证**（项目硬约定） |

- **产品要什么 / 做到什么算完** → `docs/PRD.md`（尤其 §1.2 边界、§2 D1–D6、§6 验收判据）
