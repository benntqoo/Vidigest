## 1. 背景与问题（Context）

2026-10-14 的同类项目调研显示，最直接的竞品 **BiliNote**（7.5k★）除核心转写外还提供
**MV3 浏览器插件（四件套）** 与 **云端版 / 账号体系**。在「集大成」选型中头头勾选了这两项。

但这两项与 Vidnote 已锁定的前提**不是「加功能」与「不加功能」的差别，而是「换形态」**：

| 议题 | 现状前提（2026-10-02 定稿） | 插件/云端要求的前提 |
|---|---|---|
| 进程模型 | 宿主（Rust+Tauri）spawn **常驻** Python sidecar，**JSON Lines over stdin/stdout** | 需要一个**独立的、可被浏览器访问的**入口 |
| 网络 | **零端口** —— 全程不起监听套接字 | HTTP 路线必须**开监听端口** |
| 数据位置 | **全本地**（PRD D5 / NFR-6：视频、转写稿、cookie 全部不出本机） | 云端路线必须**出本机** |
| 装机前提 | **装完即用**（PRD D1：目标机器无 Python、无 Rust） | 云端路线引入账号与网络依赖 |

⇒ 本 ADR 要回答的**不是**「插件/云端好不好」，而是：

> **它们是否值得推翻「桌面单机 + 零端口 sidecar + 全本地」这一组前提？如果要，代价与顺序是什么？**

---

## 2. 决策驱动因素（Decision drivers）

按优先级：

1. **不能破坏已验收的能力**：`docs/PRD.md` §6 已勾上的判据（断点续跑、逐字节可复现、无孤儿回收、
   离线可用）在形态变更后必须仍然成立。
2. **护城河优先于功能数量**：调研结论是现有项目**没有一个**把「无上限批量 + 运行时并发 +
   资源护栏 + 断点续跑」当卖点。**这是唯一空的生态位**；新形态不得以稀释它为代价。
3. **增量成本必须与收益成比例**：插件/云端属于**分发与入口层**的增益，不是核心链路增益。
   拿核心链路（转写 8.7× 实时、23/23 调度）去换入口便利，方向不对。
4. **可逆性**：形态变更一旦落到「已发布 identifier / 已上架商店 / 已建账号体系」，回滚成本极高。

---

## 3. 考虑的选项（Options）

### 3.1 浏览器插件「连回本机」的四条技术路线

| # | 路线 | 是否需要端口 | 生命周期归谁 | 成本 | 备注 |
|---|---|---|---|---|---|
| **A** | **自定义协议处理器**（注册 `vidigest://` URI scheme，扩展只把当前页 URL 交过去，宿主启动） | **否** ✅ | 宿主 | **低** | 只能**单向**（URL 进程序）；拿不到页面 DOM / 登录态。**作为最小可用入口，成本最低** |
| **B** | **浏览器 Native Messaging**（扩展 ↔ 本机原生宿主，走 stdio + 4 字节小端长度前缀 + UTF-8 JSON） | **否** ✅ | **浏览器**（由它拉起宿主进程） | 中 | 协议与现有 sidecar 的「stdio + JSON Lines」**同源**，最贴合现有架构；但宿主由浏览器启动 ⇒ **与「常驻 worker 由 Tauri 宿主管理」冲突**，需重新设计生命周期 |
| **C** | **本机 localhost HTTP 服务**（127.0.0.1 + token） | **是** ❌ | 宿主或独立进程 | 中高 | 要处理端口冲突、防火墙弹窗、token 鉴权、CORS；**直接推翻「零端口」** |
| **D** | 完全云端（扩展只调用远端服务） | — | 云 | 高 | 见 3.2；等于把核心能力搬出本机 |

> ⚠️ **未实测**：A/B/C 的具体可行性（注册表键位、清单格式、Windows 上的兼容性）**我没有验证过任何一条**，
> 上表是按公开机制做的**推断**。任何一条在动手前都必须先写 POC。

### 3.2 云端版 / 账号体系

| 维度 | 若做云端，需要改什么 |
|---|---|
| 架构 | 新增多租户后端（转写能力是 GPU 重资产 ⇒ 成本模型与桌面版完全不同） |
| PRD | D1（装完即用）、D5（离线可用）、NFR-6（隐私：视频/转写稿/cookie 不出本机）**三条需重写** |
| 成本 | 单条 20 分钟视频的 GPU 成本 + 存储 + 带宽；对标「一次买断/免费」的桌面版是**商业模式变更** |
| 风险 | 用户视频上云 ≠ 现在的产品承诺；一旦公开过「全本地」，再收回是**信任成本** |

**结论**：这是**商业决策**，不是技术决策。它需要的是单独一份 ADR（见 §7），而不是塞进本 ADR 或功能清单。

---

## 4. 决策（Decision）

**D-1（本期不做）**：直到 `docs/PRD.md` §6 最终验收判据**全部勾上**（M7）之前，
**不实现**浏览器插件，**不实现**云端版 / 账号体系。二者不进入 `docs/功能融合路线图.md` §3 的 P1–P5 排期。

**D-2（口径同步）**：`docs/PRD.md` §1.2 中原「云端同步 / 账号体系」一条由「**永久不做**」
调整为「**暂不做（可逆）**」，并补日期与重开条件（已执行，见 PRD §10 变更记录）。
画面内容理解（VLM）同批调整，但**不属于本 ADR 的范围**。

**D-3（顺序：先定形态，再写功能）**：若将来要做插件，**第一步是决定「本地服务化形态」**
（即 §3.1 的 A/B/C 选哪条），**并为此单独出一份 ADR（ADR-0002，待写）**。
**不允许**先写插件代码再倒推形态。

**D-4（约束：优先保「零端口」）**：在上述 ADR-0002 中，**A（自定义协议）与 B（Native Messaging）
优先于 C（localhost HTTP）**。理由：C 是唯一会推翻「零端口」这一已定稿前提的选项，
而 A/B 都能在保持 stdio 语义的前提下提供入口。**除非 A/B 被 POC 证明不可行，否则不选 C。**

---

## 5. 后果（Consequences）

**正面**

- 已验收的全部判据（断点续跑 / 可复现 / 离线可用 / 无孤儿）**不受影响** —— 本期不动它们。
- 核心链路（转写、调度）的排期不被入口层需求挤占。
- 保留将来做的可能（口径已从「不做」改为「暂不做」），且**重开条件明确**，不是一句空话。

**负面 / 代价**

- **失去了竞品已有的入口便利**（BiliNote 的插件是它的获客入口之一）。这是一次**主动放弃**。
- 若将来决定做，**成本只会更高**：插件与云端都会在 identifier / 商店 / 账号体系上产生不可逆资产。
- 本 ADR 只记录「现在不做」，**没有解决任何技术问题** —— 它把风险推到了 ADR-0002/0003。

**中性**

- 「暂不做」与「不做」在实践中容易滑成同一件事。因此 §6 的重开条件必须是**可观测的事件**，
  而不是「等有空」。

---

## 6. 重开条件（Revisit triggers）

满足**任一**即应重开本 ADR（而不是默默开始写代码）：

1. **M7 达成** —— `docs/PRD.md` §6 全部判据勾上 / `handoff.md` 里「剩余工作」清零。
2. **真实的入口需求出现** —— 出现明确的使用场景，其价值**只有插件能提供**（例如：
   需要**批量吞掉「当前浏览器已登录、但无公开链接」的页面**），且用「复制链接 + 粘贴」的成本被证实
   不可接受（要有实测，不是感觉）。
3. **分发诉求出现** —— 决定开源 / 上架商店，需要入口层做获客或留存。
4. **云端成为商业决策的议题** —— 此时**不是重开本 ADR，而是新开 ADR-0003**（云端产品形态），
   因为它要重写 D1/D5/NFR-6 三条，与本 ADR 不是同一量级。
