## 0. 一句话结论

你要的「集大成」= 把 **BiliNote / BiliSum / video-devour / ViNote** 四家的强项叠到现有 5 阶段上。
但其中 **3 项与 PRD 已锁定的边界直接冲突（画面理解、账号、云端）**，**1 项（浏览器插件）会推翻
「桌面单机 + sidecar」的架构前提** —— 后者必须单独立项，不能混在功能清单里做。

先定口径，再排期；否则这一轮必然返工（这正是你一直在避免的成本）。

> **2026-10-14 更新**：口径已定 —— **3 项冲突全部按「暂不做（可逆）」处理**，插件按「本期不做 + 立 ADR」
> 处理。故本图现在的排期是 **P1 → P2 → P3 → P4**，P5 起顺延。见 §2.1 与 §7。

## 4. 融合时要守住的 5 条底线（防「集大成」变成「样品间」）

1. **离线可用不能被破坏**：汇总 / VLM / RAG **全部默认关闭**，关掉后仍是一个完整可用的转写工具（D5 / NFR-4）。
2. **转写稿是主产物**：任何新产物不得替代或降级它（D4）。
3. **🔴 护城河不能被稀释**：调研结论是 —— 现有项目**没有一个**把「无上限批量 + 运行时并发 + 资源护栏 + 断点续跑保障」当卖点。这是唯一空的生态位，新功能不得以牺牲调度保障为代价。
4. **每个新功能都要带失败可操作提示**（D6）；VLM / LLM 失败**不算任务失败**（沿用 FR-6 约定）。
5. **口径变更走「划删 + 补日期」**，禁止静默覆盖（`docs/工程约定.md`）。
