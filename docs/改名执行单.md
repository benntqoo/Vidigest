## 2. 数据迁移（**本机已有真实数据，不能跳过**）

实测现状（2026-10-14）：

```
%LOCALAPPDATA%\Vidnote\
├── config.yaml   811 B    ← 含 2 条**绝对路径**指向旧目录
├── state.db       20 KB   ← tasks 表 2 行（断点续跑依赖它）
└── work\                  ← 已有产出
```

`config.yaml` 实测内容（关键两行）：

```yaml
paths:
  work_dir:  C:\Users\Ben\AppData\Local\Vidnote\work     # ← 必须改
  model_dir: C:\Users\Ben\AppData\Local\Vidnote\models   # ← 必须改
summarize:
  api_key_env: VIDNOTE_API_KEY                          # ← 必须改（见 §1.2 item 8）
```

**做法：一次性手工迁移，代码里不写兼容逻辑。**

理由：本机只有 2 条任务，迁移成本远低于在 `app_data_dir()` 里永久背一个「双目录回退」分支 ——
那种分支一旦写进去，将来每处路径判断都要考虑两种历史布局，且没人会记得删。

步骤：

```bash
# 1) 确认没有旧/新 exe 或 python worker 在跑（否则 state.db 被占用）
tasklist | grep -iE "vidnote|vidigest"

# 2) 改名目录
mv "$LOCALAPPDATA/Vidnote" "$LOCALAPPDATA/Vidigest"

# 3) 改 config.yaml 里的 2 条绝对路径 + api_key_env（三处）
#    路径中的 Vidnote → Vidigest；VIDNOTE_API_KEY → VIDIGEST_API_KEY

# 4) 校验（⚠️ 见 §7 偏差 1：`app/cli.py` 直接跑会 ModuleNotFoundError，dev 模式读的也是仓库根 ./state.db）
python -m app.cli list
```

**判据**：~~`python app/cli.py list` 输出的任务条数与迁移前一致（2 条），且 `work_dir` 指向新目录~~
→ **实际采用的判据（2026-10-14 修正）**：直接读迁移后的库，确认任务数与迁移前一致（**2 条**）、
`config.yaml` 的 `work_dir` / `model_dir` 指向新目录。理由见 §7 偏差 1：**dev 模式根本不用数据目录**，
`app/cli.py list` 读的是仓库根的 `./state.db`（那是另一份库，1 条任务），因此它**不能**用来验迁移。

### 7.2 与执行单原文的偏差（3 处，都是执行单写错）

1. **§2 的校验命令写错了**：`python app/cli.py list` 直接跑脚本会 `ModuleNotFoundError`

   **决定性的是 UpgradeCode**。）
