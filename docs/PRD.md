## 1. 产品定位

> **一句话**：把「一堆在线视频」批量变成「一份可检索、可引用的本地结构化文稿库」——
> **全程本地、离线、GPU 加速、装完即用**。

### 1.1 要解决的问题

| 痛点 | 现状 | Vidnote 的答案 |
|---|---|---|
| 视频里的信息 90% 在语音里，但只能「看/听」才能获取 | 20 分钟视频要花 20 分钟；100 条 = 33 小时 | GPU 转写 **8.7× 实时** ⇒ 100 条 20 分钟视频约 **4–4.8 小时** |
| 现有的转写工具都是「一次一条、网页版、要上传」 | 批量不可用；内容要出本机 | 批量 + 全本地；除可选汇总外**不联网** |
| 转完还是散的，找不到、不好引用 | 一堆 txt | 每条视频一个自包含目录（转写稿 / 拼版 / 汇总），结构统一、命名规范 |
| 批处理跑到一半失败，全白跑 | 从头再来 | 断点续跑：进程被强杀后重启，**已完成的不重跑** |

### 1.2 不做什么（产品边界的另一半）

一个工具的价值也由它**拒绝做的事**定义。以下为**明确不做**（引自 `PLAN.md` §1，并补充理由）：

- ❌ **视频转码 / 剪辑**：Vidnote 是「读取」工具，不是「生产」工具。
- ❌ **多语言**：先只支持中文。多语言会牵动模型选择、VAD、标点、基线四件事。
- ❌ **云端同步 / 账号体系**：与「全本地」的定位直接冲突。
- ❌ **画面内容理解（OCR / 视觉模型）**：抽帧的定位是**兜底**——只对付「画面有独立信息量」的
  少数视频（实测多数口播视频画面无独立信息量，故抽帧默认关闭）。
- ❌ **说话人分离、时间轴人工校对编辑器**：这是另一个产品。
- ❌ **移动端**。
- ❌ **多 GPU 并行**：见 `PLAN.md` §3.3。

### 1.3 已知并接受的代价

| 代价 | 为什么接受 |
|---|---|
| **必须有 NVIDIA GPU + CUDA** | CPU 只有 **1.44× 实时**（GPU 6.0 倍差距）：100 条 20 分钟在 CPU 上要 **23 小时**。**GPU 是前置硬要求，不是可选项** |
| 安装包 **1.45 GiB** | 代价来自把 CUDA 运行库（cuBLAS/cuDNN）随包分发。换来的是「用户机器上不需要 Python」 |
| 抖音 cookie **约 24 小时过期**（`ttwid`） | 平台侧限制。缓解：cookie 自动化重取（阶段 4）+ 失败项可重试 |
| 只出 **MSI**，没有 `-setup.exe` | NSIS 有 2 GiB 硬限制，载荷 2.5 GiB ⇒ 已判死（`docs/打包与分发.md` §3.1） |
| 首次构建要联网 | WiX 工具链自动下载；仅构建者受影响，最终用户不受影响 |

## 2. 最终目标（Definition of Done）

**产品「做完了」= 下面 6 条同时成立。** 这是本项目的北极星，所有排期都服务于它。

| # | 完成的定义 | 现状 |
|---|---|---|
| **D1** | **装完就能用**：目标机器**没装 Python、也没装 Rust**，双击安装包 → 安装 → 桌面快捷方式 → 启动即用 | 🟡 安装包已产出（exit 0）；**「干净机器」上的安装与运行未验证**（本机 Python/Rust 都在，同机模拟不算数） |
| **D2** | **100 条 20 分钟视频在一个下午跑完**（≈4–4.8 小时），坏链接不影响其余 | 🟡 吞吐已实测（外推值）；**批量只在 10 条 × 60 秒上验过**，未做长跑 |
| **D3** | **中途断电 / 强杀不丢进度**：重启后已完成的不重跑，未完成的从断点继续 | ✅ 已验收（`tools/phase2_acceptance.py`） |

| **D5** | **离线可用**：除（可选的）汇总与 cookie 重取外，全流程不联网 | ✅ 汇总默认关闭；模型与依赖全部本地 |
| **D6** | **失败可归因**：每种失败都给出「下一步该做什么」，错误提示**首行即动作** | 🟡 已做：231/5/2 已翻译、退出事件进日志区、`exited` 显示原因；**cookie 失效与磁盘不足尚无提示** |

## 3. 目标用户与使用场景

### 3.1 用户画像

**一个人**，手上有**几十到几百条**必须看但没时间看的视频（行业讲解、课程、访谈、竞品内容、
会议录像），目标是把它们**变成能搜索、能复制、能引用的文字**，然后写点什么（报告 / 笔记 / 脚本）。

特征（决定了所有设计决策）：

- **不是程序员**，不装 Python 环境、不会读 traceback ⇒ 必须打包成安装包。
- **有 N 卡**，机器内存**不算宽裕**（本机 61.6 GB 总量但**可用在 12.6–26.2 GB 之间波动**）。
- **要的是结果不是过程**：不关心用了什么模型，只关心「点了开始之后能不能不管它」。
- **会中途打断**：关机、关窗口、被别的程序抢 GPU。

### 3.2 核心场景

| 场景 | 描述 | 主要需求 |
|---|---|---|
| **A. 批量归档**（核心） | 攒了几十条链接，一次性丢进去，希望几小时后全部变成稿子 | 批量输入、并发调度、进度可见、失败可重试、断点续跑 |
| **B. 单条速览** | 只想快速知道某条视频讲了什么 | 单条也能跑；汇总模块（阶段 4）价值最大 |
| **C. 检索与引用** | 记得某个视频里讲过某个概念，要找回来 | 产出结构统一、可被系统搜索；**转写稿是主产物** |
| **D. 二次加工** | 把转写稿喂给别的工具（做笔记 / 写文章） | 转写稿纯文本、无多余包装、UTF-8、分段带时间戳 |

## 4. 功能需求

> 每条格式：**需求 → 验收判据 → 现状**。判据可复跑的命令写在末尾。

### FR-1 输入

- **需求**：接受三种输入：① 在线视频链接（抖音 / B站 / YouTube，**混平台**）② 本地视频文件
  ③ 链接文本文件（txt/csv，每行一条）。**支持一次粘贴多条**。
- **关键子需求（容易做错）**：用户粘贴的通常是**分享文案**而不是干净链接：

  ```
  8.25 复制打开抖音，看看【某创作者的作品】【标题…】…
  https://v.douyin.com/AbCdEf12345/ vFh:/ 03/30 :3pm b@n.qR
  ```

  必须抽出 `https://v.douyin.com/AbCdEf12345/` 并丢弃干扰码；**每个平台要同时覆盖短链与站内长链**
  （从 App 分享和从网页复制的形态不同）。全部规则都失败时，把整行原样交给 yt-dlp 再试一次。
- **验收判据**：粘贴含干扰码的分享文案能抽出正确 URL；混平台批量能正确识别平台。
- **现状**：🟡 实现完整（`app/core/urls.py`，逐平台正则 + 兜底），**但没有独立自测**——
  只在验收脚本里被间接用到。**这是本项目测试覆盖最薄的一块，且成本极低（纯函数、无依赖）。**

### FR-2 下载

- **需求**：调 yt-dlp 下载视频；支持 cookie（抖音需登录态）；**加速率限制**防平台风控
  （默认 ≤ 10 条/分钟，可配置）；下载失败不阻断整批。
- **验收判据**：坏链接被标记 `failed` 且不影响其他条目；风控触发时不封号。
- **现状**：✅ 下载 + cookie 文件 + 失败隔离；速率限制配置项已存在（`download.rate_limit_per_min`）。

### FR-3 音频抽取

- **需求**：从视频抽 16 kHz mono wav；**绕开 PyAV**（faster-whisper 1.2.1 与 av 19 不兼容）；
  ffmpeg 定位必须校验可执行性。
- **验收判据**：抽出的 wav 喂给转写能产出与基线一致的稿子。
- **现状**：✅ 已实现（`app/core/audio.py`）。

### FR-4 转写（核心功能）

- **需求**：中文视频转写，GPU（`large-v3` + `float16`）；输出**分段带时间戳**；产出一致性可复现。
- **关键设计**：`initial_prompt`（领域术语提示）是**强参数**——同一音频加与不加，
  产出从 681 段碎句变成 662 段整句带标点。**它必须与验收基线一起存档**。
- **验收判据**：产出与基线 `samples/transcript_gpu.txt` **逐字符严格相等**（不放宽）；
  同参数多次重跑逐字节一致。
- **现状**：✅ 已验收。**转写是整条流水线的串行瓶颈**（占比约 90%），一切并发设计围绕它。

### FR-5 抽帧拼版

- **需求**：可选（**默认关闭**）。按场景变化抽帧，拼成一张联络表（contact sheet）。
- **理由**：实测**多数口播视频画面无独立信息量**，默认开只会白花时间与磁盘。
- **验收判据**：开启后产出拼版图，目录结构统一。
- **现状**：✅ 已实现（`app/core/frames.py`），默认关闭。

### FR-6 结构化汇总（LLM）

- **需求**：可选（**默认关闭**，保证离线可用）。基于转写稿生成**摘要 + 章节大纲 + 要点**，
  调 OpenAI 兼容接口；**密钥走环境变量**（`VIDNOTE_API_KEY`），不进配置文件。
- **验收判据**：转写完成后能产出汇总文件；**汇总失败不算任务失败**（转写稿是主产物，汇总是增值项）。
- **现状**：❌ **未实现**。仅 `TaskStatus.SUMMARIZING` 枚举值与 `config.summarize.*` 配置项已就位。
- **未验证项**：一条 20 分钟视频转写稿约 8000–10000 字，**是否超出所选模型上下文、单条成本多少，
  未测**（`PLAN.md` §11.4）。**这是阶段 4 的主要未知量。**

### FR-7 调度与并发

- **需求**：无数量上限；**并发度运行时探测硬件动态决定，绝不写死**；三级流水线
  （下载池 → 转写池 → 抽帧池）+ 有界队列背压 + 内存护栏。
- **关键设计**：**转写恒为 1 并发**（GPU 单卡串行是吞吐最优解，开 2 个实例无收益）。
- **验收判据**：阶段确实重叠（重叠系数 > 1.0）；内存峰值不超可用内存 80%。
- **现状**：✅ 调度正确性已验收（**23/23**，真跑 GPU）；
  🟡 性能判据未按原口径验证（只测了 10 条 × 60 秒，不能外推到 20 分钟视频）。

### FR-8 断点续跑

- **需求**：进程被杀 / 断电后重启，**已完成的不重跑**，未完成的从断点继续；
  中途态回退到上一稳定态。
- **关键设计**：**终态只有 `done` / `cancelled`**；`failed` **不是**终态（须显式重试）；
  `cancelled` **刻意不参与回退**（否则重启后会**违背用户意愿自动重跑**）。
- **验收判据**：`taskkill /F /T` 强杀后重启，中断前已 `done` 条目的
  `status` / `updated_at` / 产出文件 `mtime` **三者均未变**。
- **现状**：✅ 已验收。

### FR-9 cookie 自动化

- **需求**：抖音 cookie（`ttwid` 约 24 小时过期）失效时**自动重新采集**，而不是整批中断。
- **关键设计**：**不能用** `yt-dlp --cookies-from-browser`（Windows 新版浏览器上基本必然失败）⇒
  用 `playwright-cli` 导出 storage-state 再转 Netscape 格式。
- **验收判据**：手动把 `cookies.txt` 改坏，程序能检测到**并自动重新采集**。
- **现状**：❌ **未实现**。目前只支持「读一个预先生成的 `cookies.txt`」，文件不存在就报错。

### FR-10 GUI

- **需求**：桌面窗口。工具栏（添加链接 / 导入文件 / 开始 / 暂停 / 重试失败项 / 打开目录）+
  状态栏（GPU 可用性、并发数、可用内存）+ 任务表格（序号 / 标题 / 时长 / 状态 / 进度 / 耗时 / 备注）
  + 可折叠日志区。
- **关键交互要求**：
  1. 添加链接支持一次粘贴多条（含分享文案抽取，见 FR-1）；
  2. 任务行**右键菜单**：打开输出目录 / 查看转写稿 / 重试 / 取消 / 移除；
  3. 关闭窗口时若有任务在跑 → **弹确认**，支持「后台继续（最小化到托盘）」；
  4. **进度条不能是假的**：每阶段上报真实进度（下载看 yt-dlp 输出，转写看 segment 时间戳）；
  5. **故障态必须如实呈现**：worker 挂了就禁用按钮、显示原因，不假装还能操作。
- **验收判据**：每处显示都能指回事件来源、随异步事件更新、鼠标键盘交互生效（已用真实窗口截图确认）。
- **现状**：🟡 主体 ✅（渲染已视觉确认、故障态已确认、右键菜单 ✅、关闭确认 ✅）；
  **「后台继续（最小化到托盘）」❌ 未实现**（依赖托盘）；本轮 4 处界面改动**尚无沙箱外复验**。

### FR-11 分发与安装

- **需求**：产出**原生安装包**，用户侧**不需要 Python 也不需要 Rust**；安装后有快捷方式、
  开始菜单项、卸载项；数据目录与程序目录分离（程序目录只读）。
- **验收判据**：在**没装 Python、也没装 Rust** 的机器上装完能双击启动 **（同机模拟不算数）**。
- **现状**：🟡 链路 ✅（`./dev.sh release` exit 0 → `Vidnote_0.1.0_x64_en-US.msi` 1.45 GiB）；
  **干净机器验证 ❌ 未做**（`docs/打包与分发.md` §6.2 有 6 条判据清单）。
- ⚠️ **改名后的落位**（读生成物核过）：安装包/安装目录/快捷方式/卸载项全是 `Vidnote`，
  **但主程序文件名是 `vidnote.exe`**（Tauri 用 cargo 包名，`productName` 不改它）。

### FR-12 可观测性与失败归因

- **需求**：日志区如实反映；崩溃/退出**必须同时进日志区**（只更新状态快照会让日志停在崩溃前最后一条，
  看起来「一切正常、然后就没了」）；**错误提示第一行必须是动作**（状态栏只渲染首行）。
- **关键设计**：**成功路径也必须留日志**（spawn、状态跃迁都打点），否则「静默死亡」完全不可观测。
- **验收判据**：231 / 5 / 2 各翻译成一句动作；**未知错误码保留系统原文**，不编听起来合理的话。
- **现状**：✅ 已实现（`cargo test --lib` 覆盖）。

### FR-13 护栏（资源保护）

| 护栏 | 阈值 | 行为 | 现状 |
|---|---|---|---|
| **内存**（第一约束） | 可用 < **2 GB** | 暂停取新任务，已在跑的跑完 | ✅ 已实现（`dispatcher.DEFAULT_MEMORY_FLOOR_GB = 2.0`） |
| **磁盘** | 剩余 < **5 GB** | 停止取新任务并告警 | ❌ **未实现**（`env_probe` 只探测上报，无调度侧拦截） |
| **GPU 被占满** | — | 提示并降级到 CPU，或排队等待，**不直接崩** | ❌ 未实现。`verify_cuda` 会如实报不可用，但无降级策略 |
| **依赖缺失** | — | **环境级故障**：中止整批，不是单条失败 | ✅ 已实现（避免空跑一整夜） |

## 8. 风险与开放问题

### 8.1 已识别风险

| 风险 | 影响 | 缓解 | 状态 |
|---|---|---|---|
| **内存是第一约束**（可用在 12.6–26.2 GB 之间波动，同日两次测量差一倍） | 并发上不去，大模型可能 OOM | 运行时动态探测 + 2 GB 护栏；建议跑批前关掉浏览器 | 🟡 护栏逻辑已测，真实负载未测 |
| **抖音反爬策略变化** | cookie 频繁失效，批量中断 | cookie 自动重取（阶段 4）+ 失败项可重试；极端情况降级为手动下载 | ❌ 未实现 |
| **平台限流** | 短时间大量请求触发风控甚至封号 | 下载池速率限制（默认 ≤10 条/分钟，可配置） | ✅ 配置项已留 |
| 磁盘占用（100 条约 8.2 GB 中间文件） | 长跑可能撑爆 | D 盘 988 GB 充足；提供「完成后删除中间文件」选项 | 🟡 配置项已留 |
| GPU 被占用 | 转写变慢或失败 | 启动时检查显存余量，不足则告警 | ❌ 未实现 |

### 8.2 开放问题（**未验证，别当成已知**）

1. **长跑稳定性**：连续 3 小时以上是否降频 / OOM —— 未测。内存护栏在真实负载下会不会触发、
   触发后恢复是否平滑 —— 未测。
2. **B站 / YouTube 的实际可用性**：**本机从未测过这两个平台**（YouTube 国内需代理，B站部分需登录）。
   建议**先只做抖音**，跑通后再扩展。
3. **批量性能口径**：10 条 × 60 秒的 1.10× 重叠系数**不能外推**到 20 分钟视频。
4. **汇总模块的 token 成本**：一条 20 分钟转写稿约 8000–10000 字，是否超上下文、单条多少钱 —— 未测。
5. **心跳在「转写进行中」是否仍通**：只测过空闲态往返（0 ms）。若转写阻塞主循环，UI 会假死 ——
   而这直接关系到「心跳判死分支要不要杀进程」。**结论未出之前，该分支刻意不杀进程、不触发重启**
   （误判会杀掉正在正常转写的任务 + GPU 上下文）。
6. **GPU 并发是否真的无收益**：「转写开 2 个实例不会提升吞吐」是基于显存与算力分时复用的
   **推断，未实测**（若阶段 2 验收达标则无必要验证）。
7. **WebView2 依赖分发性**：干净机器上是否需要用户预装 WebView2 —— 未验证。
