## 架构（2026-10-02 定稿，不再讨论）
- UI = Rust + Tauri；功能 = Python。宿主 spawn **常驻** worker（sidecar）；**JSON Lines over
  stdin/stdout**，零端口；**stdout 只走协议，日志全走 stderr**。
- `app/core/` **不感知传输方式**（不 print / 不 sys.exit / 不读 argv）。入口 `app/cli.py`（人用）
  + `app/rpc.py`（Rust 用）共用 core。进程回收走 Job Object。
- **不换 Rust 转写**（勿重开）：瓶颈是 GPU + CTranslate2(C++)；yt-dlp 无 Rust 等价物；
  PyO3 嵌入会让 CUDA DLL 污染 Rust 进程。
- **应用名（2026-10-06 改，已重跑 `./dev.sh release` 验证 exit 0）**：`productName` = **Vidnote**
  ⇒ MSI `Vidnote_0.1.0_x64_en-US.msi`、安装目录 `%ProgramFiles%\Vidnote`、快捷方式 / 开始菜单 /
  卸载项全是 `Vidnote`。⚠️ **但主程序文件名是小写 `vidnote.exe`** —— Tauri 默认用 **cargo 包名**，
  `productName` 不改它（只有显式配 `mainBinaryName` 才在 `tauri build` 里重命名）。本项目**刻意不配**：
  配了会让 `tauri dev`（debug 走包名 `vidnote.exe`）与 `tauri build`（`Vidnote.exe`）名字不一致，
  收益只是一个首字母大小写。**查进程按 `vidnote.exe`**。
  crate 名 = `vidnote`（lib `vidnote_lib`）；`app-ui/` **只是工程目录名，未改**；
  数据目录一直 `%LOCALAPPDATA%\Vidnote` ⇒ **无需迁移**。核对依据见 `docs/打包与分发.md` 开头（读
  `wix/x64/main.wxs` 生成物，不是推断）。

## Python 功能层
- **三态布尔禁止 `bool()` 收敛**：`env.cuda.usable` = `None`(未验证)/`True`/`False`。`bool(None)=False`
  会把「未知」当「不可用」→ 并发误按 CPU 规划。`rpc.py` 用 `device_count>0` 快判，验证回来再纠正。
- **`verify_cuda` 必须异步**（数秒 + 3 GB 显存）：`ready` 先返快判 + `gpu_verified:false`，随后推 `env_verified`。
- **进度契约**：耗时函数附 `on_progress: Callable[[str, float], None] | None`，cli（stderr 每 5% 一行）
  与 rpc（转 task_update）共用。`stage` 用 **TaskStatus 英文值**，中文映射归 `rpc.STAGE_LABELS`
  （core 不嵌 UI 文案）。**`on_stage`/`on_progress` 分开**：前者只在跃迁触发，后者高频、
  **限流在 dispatcher 做**。
- **状态归属单一**：`fetcher`/`audio`/`transcriber`/`frames` 不写状态、不碰 store，只抛异常；
  流转全在 `pipeline.run_one()`。
- **产出文件全部显式 `newline="\r\n"`**（基线 CRLF，逐字节比对）；`dir_name()` 补零 4 位（`0001_x`）。
- **ffmpeg 定位须校验可执行性**（存在 + 非空 + `MZ` 头）：WinGet 的 `Links/ffmpeg.exe` 是 0 字节占位，
  `which()` 命中但报 WinError 193。

### 阶段 2（调度）
- **终态只有 `done`/`cancelled`**；`failed` 不是终态（须显式 `retry`）。`cancelled` **刻意不进**
  `INTERRUPTED_ROLLBACK` —— 回退会导致下次**违背用户意愿自动重跑**。
- **`dispatcher.submit()` 会跳过 `done`**：`--force`/`--retry` 要跑的恰是 `done`/`failed`，
  入队前必须重盖 `pending`。
- **`cancel_event` 必须在阶段开始前就存在**（投递任务的锁内创建），否则跑动中取消看不到它。
- **取消是协作式的**：转写只能在 **segment 边界**中断（CTranslate2 是进程内 C++）；`TaskCancelled`
  **不是 `StageError`**，不计失败数。
- **子进程回收用 `kill()` 不用 `terminate()`**（后者对 console 程序只发 WM_CLOSE → 留孤儿 ffmpeg）。
- **依赖缺失 = 环境级故障**：`faster_whisper` 导入失败抛 `FatalEnvironmentError` 中止整批，
  否则整批空转、像「输入有问题」。
- **`pipeline` 阶段函数是调度单位**（`run_download`/`run_asr`/`run_frames`），`run_one` 只是串行组合；
  cli/rpc 走 `run_one`，dispatcher 走阶段函数 —— 共用实现，不会并行/串行不一致。抽音频不单独设池。
- **内存护栏采样点 = 「准备取新任务」时刻**；`_intake_open()` 里**不能**提前 `return False`
  （采样会停 → 永久卡死）。
- **两层去重**：`urls.extract_many` 管批内，`store.url UNIQUE` 管跨批次；`reason=duplicate` 只在跨批次出现。
- **`pipeline_state` 是 UI 生死线：每次状态跃迁都必须推事件，终态（→idle / →aborted）也不例外**
  （2026-10-06 卡死缺陷：终态不推 → UI 停在 running →「开始」按钮永久灰死，批次跑完后无法接续新任务）。
  同族三条硬约束：① `start()` 无活可干时落 **idle** 不是 running（否则没人把它翻回来）；
  ② `_put()` 必须感知 ABORTED（下游池死掉后满队列会把下载线程永久卡住，`start()` 的重铺分支
  要求线程全部退出才走得进）；③ 中止时阶段间队列里的任务要**倒回 `_pending`**（`submit()` 的
  去重只看 `_pending`/`_active`，看不见队列居民 → 恢复时会重复入队）。回归在
  `tools/dispatcher_selftest.py` 判据 12/13。

## Rust 界面层（阶段 3）
- **带副作用的 `Drop` 类型禁止 `let _x = ...`**（句柄/guard）。`JobObject` 设了 `KILL_ON_JOB_CLOSE`
  ⇒ 句柄 drop = 杀掉作业内所有进程。**指纹：spawn 日志有、pid 对，然后进程没了且无任何 stderr**。
  现存于 `Inner::job`。
- **状态与日志各只有一个发射口**：`Inner::emit_state()` / `Inner::emit_log()`，不要绕过它们 `app.emit(..)`。
  **成功路径也必须留日志**（spawn、状态跃迁都 `eprintln!`）。
- **进程回收三道，顺序不能乱**：优雅 `shutdown` → Job Object → `RunEvent::Exit` 的 `force_kill()`。
  第三道不能省（`bind_child` 失败降级为警告时 Job Object 是空的）。`force_kill` 幂等。
- **`indexmap` 依赖必须写两处**（`[dependencies]` + `[build-dependencies]`，都 `features=["std"]`）：
  resolver v2 的 Normal / HostDep feature **分开解析**，只写一处**报错一字不变**。
  改完 feature 必须 `cargo clean -p <pkg>` 再 build（否则复用旧 rmeta，现象是「改了没用」）。
- **windows-sys 的 Job Objects 分层 gated**：`CreateJobObjectW` 需 `Win32_Security`；
  `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` 需 `Win32_System_Threading`（漏了报 E0432 + 含糊提示）。
- **崩溃恢复**：`MAX_RESTARTS=1`，退避 1 s；用尽后给**手动入口**（`worker_restart` + 工具栏按钮，
  只在 `failed`/`exited` 出现）。三坑：① `Inner` 持 `Weak<Inner>`（`Arc::new_cyclic`），用 `Arc`
  自引用成环 → `Inner::drop` 永不执行；② 心跳线程用**代号 `heartbeat_gen` 换代**，重置
  `stop_heartbeat` 会**双心跳** → worker 提前判死；③ `restart_count` **单一真源 = 原子量**。
- **心跳判死分支刻意不杀进程、不触发重启**：`PLAN §11.7`「转写中能否回 pong」**未验证**，
  误判会杀掉正常转写的任务 + GPU 上下文。**测清楚再动手**。
- **三端字段要对齐**（规格 §4 `ready` 带 `pipeline_state`，前端一直在读，Rust 到 2026-10-04 才补）。
  加字段前先 grep 三端。
- **决策必须抽成纯函数**（`decide_recovery` / `needs_close_confirmation` / `hint_for_spawn_error`）：
  住在需要 `AppHandle` 的函数里就永远测不到，而那恰是唯一会错的地方。
- **关闭确认 + 优雅关闭 30 s**：`CloseRequested` → 要拦就 `api.prevent_close()`；`close_confirmed`
  是**一次性放行**；确认后**轮询 `alive` 等 worker 真退出**（`SHUTDOWN_GRACE=30s`，与 `rpc.py` 的
  `dispatcher.stop(timeout=30.0)` 对齐）才 `app.exit(0)`；期间必须有遮罩，否则强杀会截断保护中的
  那次 `state.db` 写入。**无任务在跑时走快速路径，不拦**。
- **`opener` 插件**：`opener:default` **不含 `allow-open-path`**，且 `open_path` 要过 ACL 路径 scope
  —— `work_dir` 在 `config.yaml` 里无法静态声明 ⇒ 前端直调必然 `ForbiddenPath`。正解：用插件的
  **自由函数**（不做 scope 校验），由宿主命令 `open_local_path` 代开。
- **错误提示第一行必须是动作**（状态栏只渲染首行）：231/5/2 各译一句；**未知错误码保留系统原文**。
- **右键菜单的关闭监听里 `contextmenu` 必须用捕获阶段**：否则「在另一行右键」先开新菜单再被冒泡关掉
  → 现象是「右键别的行没反应」。

## 项目约定（硬性）
- `samples/` 与 `docs/样例产出_参考.md` **本地专用**，任何时候不得 `git add -f`。
- 涉第三方视频的示例（标题 / 链接 / 创作者）在文档中必须脱敏为占位符。
- 阶段 1 判据：与基线**逐字符严格相等**，**不放宽**（基线可换代，判据不放宽）。
- **验收基线必须与其完整参数一起存档**（只存产出不存参数 = 金标准不可验证）。
- **`initial_prompt` 是强参数**：加/不加 = 681 段碎句 vs 662 段整句带标点。
- **判据必须真的被报告**：`rpc_smoke.py` 的 EOF 判据曾被 `record` 到被丢弃的 host 上，脚本显示 18/18
  却从未出现在输出里。**一个悄悄不报告的判据比没有判据更危险：它在报告成功。**
- **排除「外部拦截」假设时，判据是「它的机制在进程里可见吗」，不是「它的名字我关掉了吗」** ——
